# Where the time goes

Seventy-two readings of this engine, from sixteen agents over the four crates, 6 058 file
reads and 23.4 million tokens of work. **Not a plan.** A map of what is actually there.

## Why this exists apart from the other two files

`RTS_OPTIMIZATION.md` is the ranked work list — what to do next. `RTS_REFUTATIONS.md` is
the graveyard — what not to try, and why. **This is neither.** It is the raw finding under
each: what a file does today, read by someone who went and looked.

Sixty-nine of these seventy-two were refuted or left unjudged, and that is exactly why the
readings are kept. **A refuted proposal is very often a correct observation with a wrong
prescription.** "`JSON.parse` builds every key as a `Vec<u16>` and then rebuilds it as a
`Str`" is a fact about the parser whatever anyone proposes to do about it. When a survivor
here is eventually built, it will be built against these readings; when a refuted one is
re-proposed, it should start from the objection in the graveyard and the reading here.

## How to read an entry

Each carries five things, in the surveyor's own words:

- **Where** — the files, usually with line numbers.
- **What is there** — the mechanism as read, which is the part that keeps its value.
- **What it should be worth** — a number. **Read whether it says READ or GUESSED.** Many
  say guessed, and the ones that say read give the command.
- **How to prove it wrong** — the cheapest observation that would settle it, most of them
  one `rts ir` or one grep rather than a build.
- **What it must survive** — which of the engine's two hard constraints applies.

## The two constraints, because most of these die to one

**RTS is ahead-of-time and DETERMINISTIC** — no deopt, no bailout, no profiling; the same
source must produce the same program on every build. **The collector scans the stack
CONSERVATIVELY**, finding roots by bit pattern, so anything that changes which SSA values
are live where can silently lose one and produce a wrong ANSWER rather than a crash.

## Status, honestly

Of the seventy-two: **three survived** a three-lens adversarial panel, **forty-nine were
refuted unanimously**, three on partial votes, and **seventeen were never judged at all**
because their refuters hit a session limit. The verdicts and the objections are in
`RTS_REFUTATIONS.md`; they are deliberately NOT repeated here, so that this file stays a
record of what was seen rather than of what was decided.

Two of these entries turned out to describe defects that were live in the tree, and both
were fixed the day they were read. One of those was found not in a candidate but inside an
objection to a different one.

### α-rename a spliced body's own locals, and delete the declaration-count gate that stands in for it

**Where.** crates/rts-codegen/src/emit/inline.rs (shape_of, candidates, local_candidate, Inlinable); crates/rts-codegen/src/emit/mod.rs (thread &mut Names into the two candidates() calls and the static-method door at ~1888); crates/rts-codegen/src/emit/omit.rs (its local_candidate call)

**What is there.** shape_of already computes `locals` — every name the accepted statements declare. Mint one fresh Name per local through `Names::intern` with a spelling no source can produce, and rewrite the candidate's `statements` and `body` replacing each local's occurrences; do it ONCE per candidate, not per site, because a fresh name collides with nothing and each site opens its own `scope.enter()` layer (self-recursion is already refused by `ctx.substituting`). Then delete `candidates`' refusal `locals.iter().any(|held| declarations_of(body, *held) != 1)`. Free names are NOT renamed — a free name must keep resolving in the caller, which is exactly what `free_proved`/`ctx.omits` prove. This is the renaming pass the module header says it does not have, and it is also a FIX: two doors bypass `candidates` and therefore have no locals gate at all (`omit.rs`'s `local_candidate`, and the static-method door in mod.rs), and both miscompile on HEAD today, silently and with exit code 0. Symptom one, environment clobber: a helper declaring `const t` spliced into a body whose own `t` is captured writes the caller's environment slot — rts prints `7 6`, node `7 5`, and renaming the helper's local to `zqw` in the same file prints `7 5`. Symptom two, a name-keyed proof leaking: `ctx.integers`/`ctx.numeric` are keyed by Name, so a caller's int32-proven `t` truncates a spliced body's own `const t = x / 2` — rts prints `2,3`, node `2.5,3`. Both reproduce on target/debug/rts.exe and target/release/rts.exe.

**What it should be worth.** No row on the benchmark table moves — analytic.ts calls arrows held in an array, which this pass never reaches. The unit is one runtime crossing per call of a helper that declares a temporary: ~18–22 ns down to ~1–4. The REFUSAL is read, not guessed: `function dist(a,b){const dx=a-b;return dx*dx}` with `console.log(dist(5,2))` emits ONE __rts_call_counted (substituted); adding a module-level `const dx = 9` elsewhere in the file makes it TWO (a real call). Frequency is a crude census: 642 of the 1791 corpus files containing a function (35.8%) declare some spelling twice, counting only const/let/var, function names, class names, catch bindings and named-function parameters — `declarations_of` additionally counts arrow parameters, loop targets and destructuring targets, so the real share is higher.

**How to prove it wrong.** `target/debug/rts.exe ir` on the two-file pair above: local_twice.ts must fall from 2 __rts_call_counted to 1 while local_once.ts stays at 1. Seconds, no release build. Separately, `rts run` on the two miscompile probes must print `7 5` and `2.5,3` — if either still prints the old answer the rename is not reaching the two doors that skip the gate.

**What it must survive.** Constraint 1 (AOT determinism): purely compile-time, one rename per candidate, same program every build; nothing is deferred and nothing is decided while emitting. Constraint 2 (conservative stack scan): it admits MORE bodies into callers, which is this pass's standing risk and is why rts-codegen rule 11's four gates — a fixture written first, `rts test` compared per file against a kept binary, doctests, and the clock — are all required. The rename itself reorders no allocation. Honest cost: `ctx.claims`, `ctx.numeric` and `ctx.integers` are keyed by Name, so a renamed local carries no annotation claim and no numeric proof — a lost speculation, never a wrong answer, and strictly better than today, where those tables are consulted with the CALLER's entry for that spelling.

*Effort: medium.*

### A trailing `if (c) return A; else return B;` is the answer `c ? A : B`, and today it is a real call

**Where.** crates/rts-codegen/src/emit/inline.rs — body_shape, plus one helper beside guard_return

**What is there.** `body_shape` matches the body's last statement against `Return(Some)`, `Return(None)`, and everything else; the third arm makes the answer `undefined` and hands the `If` to `straight_line`, which refuses it because `guard_return` requires `else_branch: None`. Add an arm: an `If` whose then-arm and else-arm are each a single `return e;` — reusing guard_return's existing single-statement-block unwrap — becomes `answered = ExprKind::Conditional { condition, then_branch: A, else_branch: B }`, with `before` unchanged. Written recursively on the else-arm it folds an `else if` chain into nested conditionals. Nothing else needs building: `capture::walk_expr` already has a Conditional arm so `closed_over` and `declarations_of` handle it for free, and `choice::emit_conditional` is the same emitter a hand-written ternary uses. The equivalence is exact — the `if` is the last statement, so nothing can run between the test and the return, and only a single `return e;` per arm may be folded.

**What it should be worth.** One runtime crossing per call, ~18–22 ns down to ~1–4. Read from `rts ir` on HEAD, not guessed: `function sign(x){ if (x<0) return -1; return 1; }` with two calls plus a console.log emits ONE __rts_call_counted — both calls substituted — and the identical function written `if (x<0) return -1; else return 1;` emits THREE. The block spelling `{ return -1; } else { return 1; }` also emits 3, and a three-arm `else if` chain with three calls emits 4 (none substituted). No benchmark row moves; the shape is helper code.

**How to prove it wrong.** `rts ir` on elsereturn.ts must fall from 3 __rts_call_counted to 1, with guard.ts unchanged at 1 as the control. One command each, no release build. If a body with a non-return statement in one arm also drops, the unwrap is too permissive.

**What it must survive.** Constraint 1: a syntactic rewrite taken at compile time, same program every build. Constraint 2: no new liveness shape — the conditional emitter is the one already used for `c ? A : B`, so the spliced body is exactly what the caller would have had if the helper had been written with a ternary. The clause to hold is the single-`return` restriction on each arm; a block with a declaration and a return must stay refused until candidate 1 ships, because that declaration is a local.

*Effort: small.*

### An arrow helper's `this` IS the caller's `this` at the omit door, and only there

**Where.** crates/rts-codegen/src/emit/omit.rs — the `local_candidate(function, length, name, arguments, false)` call; the clause it turns on lives in inline.rs (`this_ok` in shape_of/closed_over)

**What is there.** Pass `function.captures_this` where omit.rs passes `false`. `omit::omittable` has already proved, over the whole body and before any of it is emitted, that the helper is declared HERE, is never read as a value and is not captured — so every call to it is in the declaring function — and `helper_bindings` never descends into a nested function, so the arrow's enclosing function IS the body being emitted. An arrow takes `this` from where it was written, which is that function, so the `this` the spliced body reads is the same one it would have captured: `emit_substituted` has `receiver: None`, does no `swap_this`, and `ExprKind::This` resolves through `scope.this_value()` — or through `scope.late_this()` in a derived constructor, which names the same binding. A non-arrow function expression must keep `this_ok = false` because its `this` is decided by the call, and `captures_this` says exactly that. `arguments` stays refused by name: an arrow's `arguments` is also the enclosing function's, but materialising it is a different question and the second door already documents that refusal.

**What it should be worth.** One crossing per call of an arrow helper that reads `this`. Read from `rts ir` on HEAD: `class C { constructor(){this.k=3;} m(n){ const scale=(v)=>v*this.k; return scale(n)+scale(n); } }` with `o.m(4)` emits FOUR __rts_call_counted (o.m, scale, scale, console.log); the same method with `v * 3` in place of `v * this.k` emits TWO. So `this` alone costs the two `scale` crossings, ~36–44 ns in that program. Frequency across real code is a guess — the shape is a helper arrow inside a method — but the per-call price is the door constant, which is read.

**How to prove it wrong.** `rts ir` on arrow_this.ts must fall from 4 __rts_call_counted to 2, with arrow_nothis.ts unchanged at 2. If it does not move, `this_ok` is not the only gate and something else in `closed_over` is refusing the body.

**What it must survive.** Constraint 1: compile-time, no guard, nothing to bail out to. Constraint 2: unchanged — this admits a body that was already going to be spliced but for one arm of `closed_over`. The failure to watch for is a non-arrow helper slipping through, which would read the CALLER's `this` for a callee whose `this` the call decides; `captures_this` is the tree's own answer to that and is the one field arrows actually change. A fixture asserting values (never asserting that a substitution happened) is gate 1 of rule 11 here.

*Effort: small.*

### A loop with no `return` inside it, and the `i++` refusal that stands in front of it

**Where.** crates/rts-codegen/src/emit/inline.rs — closed_over (the Update arm), straight_line_at, declared_names, closed_over_statement; depends on candidate 1 and should not ship before candidate 5

**What is there.** Four changes, and the first is worth doing whether or not the rest lands. (a) `closed_over`'s `ExprKind::Update` arm returns false when the target name is in `bound`, while the `Assign` arm four lines above admits precisely the same write — and the Assign comment names `let seen = 0; seen++` as the shape it exists for, which is the shape the Update arm refuses. `unary::emit_update` on an `Ident` is `binding::read` then `binding::write`, the identical path an `Assign` to an Ident takes, so the refusal is unproved rather than a boundary. (b) `straight_line_at` admits `While`, `DoWhile`, `For` and `ForEach` when the loop's subtree holds no `Return` at any depth and no LABELLED `break`/`continue`; an unlabelled break or continue is contained by the loop's own frame, which `stmt::emit_stmt` pushes, and a label outside the loop is unreachable because `Labelled` stays refused. (c) `declared_names` and `closed_over_statement` gain the same arms, which is what keeps the three lists from drifting — the file already records that adding a kind to one and not the other refuses rather than admits. (d) The loop head declares its target, so this only pays on top of candidate 1: `for (let i…)` in any program with two loops has `declarations_of(i) ≥ 2`.

**What it should be worth.** One crossing per call, ~18–22 ns, honestly amortised: a helper with a loop does O(n) work per call, so this pays where the helper is called often and its loop is short. RTS_OPTIMIZATION item 9 prices it at 24.50 ns/call. The refusals are read: `function total(n){let s=0;for(let i=0;i<n;i++)s=s+i;return s}` emits TWO __rts_call_counted and the same helper with the loop replaced by `s = s + n` emits ONE; `function bump(n){let s=n;s++;return s}` emits TWO and `s = s + 1` emits ONE. No benchmark row moves.

**How to prove it wrong.** Two `rts ir` runs, no release build. loopbody.ts must fall from 2 __rts_call_counted to 1 — AND the same helper with a `return` inside the loop must STAY at 2. If the second one also drops, the Return scan is not reaching, which is the nested-guard miscompile widened: straight_line_at's own comment records what that cost, a program that printed nothing and exited zero.

**What it must survive.** This is the change that most needs rule 11's four gates, and constraint 2 is the sharp one: a loop spliced into the caller changes which SSA values are live across a back edge in the CALLER's frame, and compiled-frame roots are found by bit pattern from a conservative scan. Constraint 1 is satisfied — the admission is syntactic and taken at compile time. It must not ship before candidate 5, because a loop body is the largest thing this pass would copy and nothing currently bounds emitted size. Sub-change (a) is independently safe and independently confirmed, so it can be gated and measured on its own first.

*Effort: large.*

### Bound emitted SIZE, because STATEMENT_BUDGET bounds nothing and the product is unbounded

**Where.** crates/rts-codegen/src/emit/inline.rs (STATEMENT_BUDGET, Inlinable, emit_substituted); crates/rts-codegen/src/emit/mod.rs (a counter on Ctx, reset per body where function::emit_body installs the other per-body facts)

**What is there.** `STATEMENT_BUDGET = 8` bounds the source statements of ONE body, and the corpus says 99.4% of named functions have 7 or fewer, so it bounds almost nothing. The quantity that actually explodes is the PRODUCT down a chain, and nothing bounds it: `ctx.substituting` is a cycle check on a name, not a depth or growth bound. Measured on HEAD with `rts ir`: sixteen helpers, each one statement, each calling the next twice, emit 1 048 616 `Call` instructions from a 17-line source, against 16 406 for the ten-helper version — 2^n. Give `Inlinable` a node count computed once in `shape_of`, give `Ctx` a per-caller budget reset where the other per-body facts are installed, decrement it by that count at each accepted substitution, and refuse when it is spent. That is the bound a C++ compiler uses, and it is the honest one here for a second reason: RTS_OPTIMIZATION item 4 says the cold-block layout question is about emitted bytes, and every other item on this list makes bodies bigger.

**What it should be worth.** 0 ns/op on every row — this buys nothing at run time and says so. What it buys is compile time (item 11's measured 59.5 s, and the 2^n above) and a ceiling on I-cache growth, and it is the precondition for candidate 4, which copies the largest bodies this pass has ever admitted.

**How to prove it wrong.** The chain generator: emitted `Call` count must stop growing once the budget is spent, while chain10 keeps the 16 406 it emits today. `rts ir | grep -c` on a debug binary, seconds. If a ten-helper chain LOSES substitutions it has today, the budget is set too tight.

**What it must survive.** Constraint 1 is the one to argue, because a budget LOOKS like a JIT heuristic: whether a given site substitutes depends on how many sites preceded it in the same caller. It is still a function of the source alone — emission order is deterministic and nothing is measured at run time — so the same source produces the same program on every build, and there is nothing to bail out to. Constraint 2 is untouched: refusing a substitution is always the shape that was already correct. The trap to avoid is bounding source statements again under a new name; the count must be over what is EMITTED, which is why it belongs on Inlinable and not on a constant.

*Effort: medium.*

## How far the receiver proof reaches

> WHAT I DID NOT PROPOSE, AND WHY. `this.m()` inside a sibling method. Refused today because `receiver_of` requires an `Ident` object. It is sound only under a clause list larger than the four candidates above: C once-declared, never read as a value, in `ordinary`; NO class in the program spells `extends C` (a subclass's own field, accessor or method shadows, and heritage is deliberately not a value read, so the existing machinery cannot see it); and — the expensive one — EVERY `new C()` in the program is the initialiser of a const that is itself a decided receiver, because otherwise an instance escapes and `inst.other.call(hostile)` gives a `this` that is not a C. That last clause is a new whole-program fact (all construction sites, all decided), not a new arm on an existing one. It is the most common method-call shape in real OO code and it moves no row in bench/analytic.ts. I left it out because candidate 1 must land first: its premise is "an instance of C has C.prototype and C's methods", which is exactly the premise five confirmed wrong answers show is not being checked. A class-field receiver, `this.helper.run()`. Needs the field written exactly once, at its declaration, with `new H()`, and read ONLY as a call receiver — a `const h = this.helper` hands out the object and `h.run = f` follows. That is a per-field version of the whole analysis plus a `this` proof, so it inherits everything the paragraph above needs and adds an escape analysis on the field. Large, and gated behind the same fix. `C.make().m()`. The receiver is a call, so the fact needed is what a static method RETURNS — type inference over a function body, not a spelling proof. Different machinery, no measured number behind it, out of this angle. `Array.isArray(o)` as an exempt position. Sound in the language (the native retains nothing and calls nothing), but it needs a list of natives that do not retain their argument — a second source of truth for something the engine does not otherwise write down — plus `primordial::untouched(Array)`. Refused on the survey's own rule about second sources. `o == null` as an exempt position. Sound per specification, which calls zero conversions when one side is null or undefined. Not proposed, because this repository has a recorded case of the runtime running `ToPrimitive` on the object for exactly that comparison, and `ToPrimitive` reaches a `valueOf` the class may declare — user code holding the receiver. If it were exempted it would need the chain to declare no `valueOf`, no `toString`, no `Symbol.toPrimitive` and no computed key, and even then the exemption would rest on the runtime's current arm order rather than on the language. `docs/codegen/entry-tax.md` part five is the class. A module-level `let` never reassigned. The lever exists — `capture::walk_expr` yields an assignment's place as an ordinary child, so `o = x` already records `o` as read as a value and a `let` receiver would be refused wherever it is written. What stopped me is that `const` and `let` differ here in TDZ rather than in reachability, and I could not price the shape: I found no row and no corpus evidence that a module-level `let` singleton is common enough to be worth widening a proof for. If it is wanted it is two lines and the same falsifier grid. A NOTE ON THE INSTRUMENT. ### receiver.rs decides five shapes WRONGLY — six confirmed wrong answers against Node, all in code that shipped hours ago

**Where.** C:/Users/danie/Documents/GitHub/rts/crates/rts-codegen/src/emit/receiver.rs — the chain walk in `resolve` (lines 148-187) and the `ordinary` filter (109-127)

**What is there.** The walk collects `ClassElement::Method` with `MethodKind::Normal`, non-static, plain key, and `continue`s past everything else. Five things it walks past are shadowing elements, so it hands the call site the WRONG function. (a) A non-static FIELD: `class D extends B { m = () => 2 }` — the field is an own property installed by the constructor and shadows `B.prototype.m`, but `ClassElement::Field` is skipped and the walk climbs to B. (b) A GETTER of the same name: `MethodKind != Normal` is `continue`d rather than terminating the key, so a derived `get m()` lets a base `m()` be substituted. (c) A non-static COMPUTED key: `plain_key` returns None and the walk carries on, so `class C { m(){1} ["m"](){2} }` substitutes the first. (d) A CONSTRUCTOR that returns an object: nothing inspects the constructor's returns, so `new C()` binds something that is not a C instance while `o.m` is resolved on `C.prototype` — and this holds through `extends`, since a base returning an object becomes the derived `this`. (e) The constructor itself is a `MethodKind::Normal` non-static method keyed `constructor` (`Method::is_constructor` confirms the shape), so it enters the map and `o.constructor()` runs its body where the language throws — which is exactly what `emit/class.rs`'s `MarkClassConstructor` exists to enforce. The fix is one rule plus two class-wide clauses: the FIRST class in the chain that mentions the key at all decides it — a normal non-static method is taken, anything else (field, accessor, private) ends that key — and a class with any non-static computed key, or with a value-returning constructor anywhere in its chain, decides nothing; skip `is_constructor` when filling the map.

**What it should be worth.** 0 ns saved. ### The environment a WRITING helper keeps — and the comment that explains it is wrong about this emitter

**Where.** crates/rts-codegen/src/emit/omit.rs (`assigns_anything_free`, and the comment at lines 156-176), crates/rts-codegen/src/emit/loops.rs (`assigned_in_expr` at 956, `assigned_positions`, `plan`, `plan_including`), crates/rts-codegen/src/emit/inline.rs (`Inlinable`, one new field)

**What it must survive.** This is the one that actually meets constraint 2. Removing a name from `captured` moves it from a heap cell to an SSA value or a block parameter, which changes which values are live where — precisely the hazard `docs/engine/lost-roots.md` names, and precisely what "reordering allocations, hoisting a load past a safepoint" describes. ### A DEFAULTED parameter, refused body-wide where `emit_substituted` refuses it per site

**Where.** crates/rts-codegen/src/emit/omit.rs (`helper_bindings` line 315, and the `spread_calls` walk at 379-420 that the new check rides along with)

### An object literal's method: closed twice by `escape.rs`, and the door that would open it is `receiver.rs`'s

**Where.** crates/rts-codegen/src/emit/escape.rs (`flattenable` at 481, and the `Call` arm of `scan_expr` at 777), crates/rts-codegen/src/emit/receiver.rs (`resolve`, `constructions`)

**How to prove it wrong.** Already run: `rts ir` on `function outer(x){ const h = { m: (y) => y + 1, k: 2 }; return h.m(x) + h.k; }` lists `__rts_object_new`, `__rts_closure_new` and `FuncId(5) m` as callees, and `rts run` answers 9. **Where.** crates/rts-codegen/src/emit/primordial.rs (one walk returning a SET of disturbed names instead of a bool for one name); crates/rts-codegen/src/emit/mod.rs (Ctx: `math_primordial: bool` at line 578 becomes `undisturbed: HashSet<Name>`, plus a per-function `globals_at_entry: HashMap<Name, ValueId>` saved/restored around nested bodies the way `ctx.substituting` is); crates/rts-codegen/src/emit/globals.rs::force_read (line 348); crates/rts-codegen/src/emit/function.rs::emit_body_into (line 918, which already receives `entry: BlockId`). ### The machine-side effect annotation and its LICM pass — the design, and the census that prices it at almost nothing

**Where.** Would be: crates/rts-codegen/src/runtime/effects.rs (new, beside raising.rs, the classification); crates/rts-cranelift/src/ir/func.rs::Signature (a flag riding beside `may_suspend`, which is the existing precedent for a per-callee property); crates/rts-cranelift/src/ir/motion.rs (new pass) called from crates/rts-cranelift/src/target/mod.rs::plan. Read first: crates/rts-cranelift/src/ir/inst.rs:607, crates/rts-cranelift/src/gc/liveness.rs.

**What is there.** The classification is the language's, exactly as `raising.rs` is: rts-cranelift depends on SWC and nothing else and cannot see one line of rts-core, so "does `__rts_type_of_is` read mutable state" is stated language-side and asserted symbol-by-symbol in rts-host, the same shape `CANNOT_RAISE` already has. The flag rides on `Signature`, not on the call site — rule 9 of the machine README says effects are declared and a caller can neither force nor decline one, and `may_suspend` is already a per-callee flag on that struct. The pass is loop-invariant code motion and NOT CSE (see the census below), and the GC rule that makes it survivable is precise: **hoisting must be monotone in liveness.** Moving a call to a preheader shortens its operands' live ranges, and shortening is the only direction a conservative frame scan can lose a root in; lengthening merely over-retains. So the pass hoists the call to the preheader AND threads each operand through the loop's block parameters, so every operand is an argument on the back edge and is live in every iteration exactly as it is today. Under that rule the emitted frames hold a superset of the words they hold now, which is the safe half of the asymmetry docs/engine/lost-roots.md describes. Everything else the annotation would license — deleting a call, CSEing two calls, sinking one past a branch — shortens something, and is refused.

**What it should be worth.** GUESS for the corpus, READ for the falsifier's own program. `scratchpad/probe3.ts`, release, min of 9 over 3M: `for(...) if (typeof x === "string") s++` with x invariant costs 18.000 ns against 2.000 hoisted by hand — **16.0 ns**, one full crossing; the `"object"` form is 15.0. So the item's own example is worth 16 ns per iteration. The corpus does not support it: `rts ir bench/analytic.ts` has 7 `__rts_type_of_is` calls and **zero** with a loop-invariant operand. Ranked below the two candidates above because those need no machine change and have their populations measured.

**How to prove it wrong.** **The falsifier RTS_OPTIMIZATION states is malformed, and checking it was the first thing I did.** On `for (let i=0;i<n;i++) if (typeof x === "string") s++`, `rts ir` today shows `Call { callee: FuncId(5) }` (`__rts_type_of_is`) exactly ONCE — in `block2`, the loop body, reached from the loop test in `block5`. It shows it once because a loop is emitted as a CFG loop; a static occurrence count can never distinguish hoisted from not-hoisted, so "once, not N times" passes today and would pass under any implementation. The correct falsifier is the BLOCK: the call must appear in `block0` (or in a block that dominates the loop header and is outside the loop), and must be absent from the body block the loop test branches to. Second falsifier, for the GC rule: `gc::describe_frames` on the function before and after must report a root set at each safepoint that is a SUPERSET of the old one — a unit test in crates/rts-cranelift/tests/safepoints.rs, no release build.

**What it must survive.** Both constraints, and it is the candidate most exposed to them. **Constraint 1**: nothing here speculates — invariance is proved from the IR's own SSA and dominator structure, the same program is emitted every build. **Constraint 2** is the reason for the liveness-monotone rule above, and the rule is checkable with `gc::Liveness`, which already exists. Note also what the annotation does NOT buy, because I looked: `Inst::is_safepoint()` (ir/inst.rs:607) returns true for every `Inst::Call`, and its ONLY consumer is `gc::describe_frames`, which `rts-core/src/entry/roots.rs:266` says nothing wires to a live frame; `frame::plan_suspension_with` (frame/mod.rs:169) uses `is_suspend()`, not `is_safepoint()`. So a `NO_ALLOC` bit has zero run-time consumers today and must not be sold as one.

*Effort: large.*

### Admit the two allocators to `CANNOT_RAISE` — a compile-time claim, not a run-time one

### `pending_arguments` is pushed by every call to shadow a vector almost no call has — stamp the depth instead and stop pushing

### The chain resolver cannot see an own property past slot 13 — and answers the prototype's instead

**Where.** crates/rts-core/src/entry/cache.rs — `cache_resolve_indirect`, the `&& slot < width` clause of the own-property arm (~line 600), against `cache_resolve`'s `Reaches::Overflow` arm (~line 362) which already answers the same case

### A decidable class's constructor is a REAL JS call on every `new` — substitute it at the site behind a new `ConstructBare` entry

**Where.** crates/rts-codegen/src/emit/call.rs (emit_construction), crates/rts-codegen/src/emit/receiver.rs (the decidability search, reused), crates/rts-codegen/src/emit/inline.rs (straight_line, reused), crates/rts-codegen/src/emit/scope.rs (Scope::swap_this, reused), crates/rts-cranelift RuntimeOp table, crates/rts-core/src/entry/functions.rs (construct_inner)

**What is there.** `rts ir` on `class Empty {}` shows the engine emits `FuncId(10) Empty`, a compiled function whose entire body is `Return(undefined)`, and `__rts_construct` runs it through `functions::invoke` on every `new Empty()`. `class Callee { v = 1 }` emits a body of exactly one `CachedSet`. So a `new` of a class the program decides pays a full activation — three per-activation stacks, the callee resolution, the throw check — to run a body the compiler is holding in its hand. The fix is the shape `receiver.rs` already shipped for methods, moved one node over: split `construct_inner` so that a new entry point does everything except `invoke` (the constructible check, the `new.target` push, the `C.prototype` read, the allocation, the link), and let `emit_construction` emit the field initialisers inline at the site with `this` bound to the returned value by `Scope::swap_this`. The clause set is smaller than `receiver.rs`'s: `C` is declared exactly once as a class, is never the target of an assignment, has no `extends`; the constructor body is `straight_line`, mentions no `new.target`, `arguments`, `super`, `eval` or `with`, has no default/rest parameter, and never `return`s a value (which is what keeps `construct_inner`'s "a returned object wins" clause vacuous). The receiver need NOT be non-escaping — the object is still really allocated and really linked, so `o` may be passed anywhere. `C.prototype` is still read at run time by the entry point, so reassigning it is honoured.

**What it should be worth.** −19 ns on `alloc class instance` (80.5 → ~61), a 24% cut. READ, not guessed: on the same release binary and the same run, a real non-substituted JS call measures 19.02 ns against a 0.96 ns floor; `new Empty()` is 51.28 at n=20 000 (below the region, no collection) and `new Callee()` 57.75. Every `new` of a user class in the corpus pays the same 19.

**How to prove it wrong.** Already half-run: `target/release/rts.exe ir` on a two-line file must show the class constructor as its own `FuncId` with a `Return(undefined)` body and `__rts_construct` in the callee legend — it does, at FuncId(10)/FuncId(11). The cheap disproof of the SIZE is the pair `new Empty()` 51.28 vs `real call g(a)` 19.02 measured in one process: if the invoke were already cheap inside `construct`, `new Empty()` would sit near `Object.create(P)` minus the native-call floor, and it does not. After the change, `alloc class instance` must fall by ≥15 ns or the claim is wrong — rule 11's fourth gate, the clock, is the one that decides it.

**What it must survive.** Constraint 1: the whole proof is a syntactic whole-module search decided while emitting, no cache steers it, the emitted program is identical on every build — the same argument `receiver.rs` makes. Constraint 2: the fresh cell stops living as a `u64` in `construct_inner`'s Rust frame and starts living as a compiled SSA value across the field initialisers; it is the receiver of every one of those writes, so it is live by construction and found by the ordinary conservative scan exactly as every `ObjectNew` result already is. The standing cost is RTS_OPTIMIZATION item 12: the constructor frame leaves `.stack`, the same trade `emit/inline.rs` already takes.

*Effort: large.*

### A typed array recomputes its four-property layout from the root shape on every object made — memoise it

**Where.** crates/rts-core/src/entry/buffers/mod.rs (attach, install_internal_bytes, install_metadata), crates/rts-core/src/entry/mod.rs (one Context field)

**What is there.** `attach` walks `shapes.root()` through four transitions — `byteLength`, `byteOffset`, `length`, `buffer` — asking `well_known` for each name, `shapes.transition` for each step and `shapes.slot_of` for each slot, then mints the type and writes the four values. Every one of those answers is a constant per kind-class (Raw takes two of the four, everything else all four), and it is recomputed per object: eight FxHash lookups and six shape-chain walks for a number that cannot change. `install_internal_bytes` does the same twice for the backing buffer. Hold the answer instead — `(ShapeId, [u32; 4])` for the two cases, computed on first use from the same shape tree — and `attach` becomes `views.set`, one `typed_as`, one `set_type` and four `set_field`s. Precedent is in the same file: `array_buffer_prototype` is a memo added for exactly this reason, with a comment saying the scan it removed was paid per buffer.

**What it should be worth.** An A/B in one process prices the removable part directly: `new Uint8Array(ab)` (four metadata properties, no buffer allocated) is 248.04 ns and `new DataView(ab)` (two, same path, same everything else) is 187.89 — 54 ns for two properties, **27 ns per property**, READ. Of that 27, `well_known` + `transition` + `slot_of` are removed and `set_field` is not; I estimate 15–20 of the 27, so **60–80 ns off `binary subarray 64`** (209.6 at n=20 000, 251.2 at the benchmark's own count), the same off `new Uint8Array(ab)`, ~40 off `new DataView`, and ~40 more off `binary alloc Uint8Array 64` (466–605) through the buffer's own two. The split of the 27 is the guessed part; the 27 itself is not.

**How to prove it wrong.** If the 27 ns per property is mostly `region.set_field` rather than the three lookups, the memo buys almost nothing. Cheapest check before writing it: `binary subarray 64` must move by ≥40 ns. A pre-build check that costs nothing is already done and is what makes this worth writing at all — the rival hypothesis, that `typed_classes::ensure`'s linear scan of `context.classes` by class NAME was the cost, was tested by running the identical `subarray` loop in a program that had registered ~28 more classes first: 216.60 vs 207.91 ns. REFUTED; do not re-propose it.

**What it must survive.** Constraint 2 is the one it must survive and it survives by holding no reference: the memo is a `ShapeId` and four slot NUMBERS, so it adds nothing to `roots::context_roots` or `trace::edges_of` and cannot be the missing line rule 10 warns about. Constraint 1: `ShapeTree` only ever grows — `remove` mints a new id rather than rewriting a node — so a memoised transition result is stable for the life of the context and the same program is emitted either way; this is runtime state, not an emission decision.

*Effort: small.*

### `new ArrayBuffer(n)` writes its two properties through the general `objects::put` where the function beside it uses the fast layout path

**Where.** crates/rts-core/src/entry/buffers/mod.rs (install_bytes, install_metadata)

**What is there.** `install_internal_bytes` was given a fast path — build the two-property shape in one walk, mint the type once, write the slots — and `install_bytes`, the public `new ArrayBuffer` path four lines above it, was left on `stamp` + `flag`, which is two `objects::put`s. `put` on a fresh cell pays an integrity check on an object nothing has frozen, an accessor walk on one that has none, and `reconcile_length`'s `well_known("length")` before every write. ### The instance never escapes and could be scalars, but the proof needs the constructor gone first

**Where.** crates/rts-codegen/src/emit/escape.rs, crates/rts-codegen/src/emit/receiver.rs, crates/rts-codegen/src/emit/function.rs (emit_body, where escape::analyse runs)

**What is there.** `escape.rs` replaces an object LITERAL bound to a local whose every occurrence is `o.k` or `o.k = v` with one ordinary binding per property, and that is why `alloc object literal 2` is 1.0 ns. A `new C()` is refused only because the initialiser is a `New` node, not because the analysis is weaker: the escape test is already an allow-list that kills any bare identifier, so `o` is protected by exactly the same walk. What is missing is the initial VALUE of each property, which for a literal is written at the site and for an instance is produced by the constructor. So this is candidate 1 plus one step: once the constructor body is admitted and its `this.f = e` writes are emitted at the `new` site, those writes are `o.f = e` on a local with known keys — precisely what `Escaping` already accepts. The extra clauses are the ones the object's identity buys: refuse if `o` is ever compared, `instanceof`'d, `typeof`'d, spread, or reaches any method call, because a scalar-replaced instance has no prototype to reach — which is stricter than `receiver.rs`, whose substituted `o.m(x)` bodies read `this.f` and would each need the same rewrite.

**What it should be worth.** `alloc class instance` 80.5 → the object-literal number, ~1–4 ns. That is a −75 ns ceiling and it is the largest single figure in this angle. It is partly a READ — the row is measured at 80.48 and `alloc object literal 2` at 1.0 — and partly a guess, because how much of the corpus actually satisfies the clauses is uncounted. Every `new C()` that fails one clause keeps candidate 1's −19.

**How to prove it wrong.** Census before building: grep the corpus for `const <id> = new <Ident>(` and count how many of those receivers occur ONLY as `o.<name>` reads and writes. If the answer is a handful, the whole thing is worth less than candidate 1 alone and should not be built. The correctness falsifier is `escape.rs`'s own: a fixture written first that asserts values and never asserts that a replacement happened, plus rule 11's four gates — the third of which (`rts test` per file against a kept binary) is what caught the last extension of a substituting pass.

**What it must survive.** Constraint 1: the replacement is decided by one collection pass and one escape pass at compile time, same program every build — `escape.rs`'s header already argues why no fixpoint is needed and the argument carries over unchanged. Constraint 2 is the sharper one and it cuts both ways: removing an allocation cannot lose the root of an object that no longer exists, but it moves every LATER allocation in the program, and this repository has a recorded case of a program's answer depending on allocation order across binaries. So the gate is a per-file corpus comparison against a kept binary, never a net number.

*Effort: large.*

### The sweep touches twenty-one dense side tables for every dead cell

**Where.** crates/rts-core/src/entry/collect_cycle.rs (release), crates/rts-core/src/heap/aside.rs, crates/rts-core/src/entry/mod.rs (the 21 Aside fields)

**What is there.** `release` clears 21 `Aside<T>`s per freed cell, and an `Aside` is a dense `Vec<Option<T>>` indexed by cell, not a hash map — so a cell that was never a proxy, a cursor, a generator, a regex, a bound function, a collection, a view or a boxed primitive still costs a load in each of those tables. Summed, the entry widths are on the order of 500 bytes per cell across all 21, which is roughly eight cache lines touched to free one 128-byte cell, and on a heap that is 96% garbage that is 63 000 cells' worth per cycle. The removal is to fold the tables that only a small minority of cells ever use — `proxies`, `cursors`, `bound`, `collections`, `generators`, `helpers`, `regexes`, `accessors`, `integrity`, `attributes`, `derived`, `boxed`, `foreign`, `detached` — into one `Aside` of a rare-payload index, so the sweep visits one table instead of fourteen. That is fewer tables, not a bit beside them: a bitmask mirroring which asides a cell uses would be a second source of one fact, and a stale bit there is the silent-wrong class rather than a slow one.

**What it should be worth.** Up to −20 ns on every allocating row. The collector's amortised share is READ by scaling the same loop across the region boundary: `new Callee()` costs 57.97 and 57.69 ns/alloc at n = 20 000 and 40 000, where the 65 536-cell region never fills and no cycle runs, and 79.05 / 80.02 / 82.08 / 89.49 at 60 000 / 200 000 / 1 M / 4 M — so the collector adds 21–31 ns per allocation. Marking is proportional to the live set, which is a few thousand here, so the sweep is nearly all of it. How much of the sweep is the 21 tables rather than `region.free` is the guessed part.

**How to prove it wrong.** `Aside::reach()` is already public and returns how far each table was ever grown. Print all 21 at exit under `RTS_GC_DEBUG` and run `bench/analytic.ts`: if only three or four tables reach the cells being swept, the other seventeen `remove`s are a length compare on a hot Vec header and this candidate is dead before any code is written. That is one `eprintln!` and one run, no release build of the engine's optimiser needed.

**What it must survive.** Constraint 2, head on — this IS the collector, and `docs/engine/lost-roots.md` records that adding one `eprintln!` inside `collect` changed a program's answer. The change must not alter WHICH cells are freed or WHICH side entries are cleared, only how many tables are visited to clear them; every payload that moves into the merged table needs its arm in `trace::edges_of` carried over, and the four mechanical checks in that document are the gate rather than a green suite. `detached` in particular is not a leak if forgotten but corruption — the comment in `release` records the 80 000-iteration program that proved it. Constraint 1 does not apply.

*Effort: large.*

### Let the chain resolver answer for a TEXT receiver — the one prototype substitution that cannot collide

**Where.** crates/rts-core/src/entry/cache.rs (`cache_resolve_indirect`, the refusal at line 666 and the doc comment above it that states the rule being changed). Reads, unchanged: crates/rts-core/src/entry/objects.rs `inherited_from`, crates/rts-core/src/entry/roots.rs:147, crates/rts-core/src/entry/context.rs:162 `shape_of`.

**What is there.** `o.m()` emits `emit_read_indirect` -> `cached_get_indirect` -> `cache_resolve_indirect`. That resolver refuses every string receiver at `let Some(link) = context.prototype_at(cell) else { return refuse("the receiver has no recorded link") }`, because a string cell carries no prototype word — `inherited_from` substitutes `string::prototype_of` by KIND instead. So the site writes the REFUSED marker and every subsequent `s.charAt(i)` pays two crossings before the call: one into the resolver (borrow, key lookup, four region probes, read the marker, return -1) and one into `GetProperty` for the full slow walk. The change is to substitute the same prototype the walk substitutes: when `prototype_at` is absent AND the cell's type is `text_type_index()`, use `string::prototype_of(context)` as the link and continue into the existing one-or-two-step loop unchanged. The refusal's own comment says why this is refused in general — arrays, callables and plain objects share undiscriminated shape types, so a site warmed on one would recognise another — and TEXT is the single kind that argument does not reach: `Context::shape_of` returns `None` for the text type by construction, so no shaped object can ever present a text header, and every text cell's header is byte-identical (`header_word(text_ty, INLINE_SLOTS)`), which makes one warmed site serve every string in the program. Nothing can shadow the answer: `put` is a no-op on a shapeless cell, and `length`/index reads are answered by `string_property`/`string_element` on a different route that this terminator never takes. The comment at cache.rs:666 must be rewritten in the same change, since it currently states a rule the code would contradict.

**What it should be worth.** READ, by substitution on target/release/rts.exe: the same native called on a receiver whose chain the cache CAN serve (`new String(s)`, which has a recorded link) against the primitive. charAt 72.48 -> 39.10 (33.4), slice(0,16) 177.38 -> 143.05 (34.3), toUpperCase 173.57 -> 137.33 (36.2), charCodeAt 59.13 -> 36.72 (22.4), indexOf 99.18 -> 87.74 (11.4). Board rows: `string charCodeAt` 59 -> ~37, `string slice 16` 162 -> ~128, `string toUpperCase 16` 161 -> ~125, `string indexOf 256` 103 -> ~92, `string split 16` 1208 -> ~1175, and `regex replace` / `regex exec+group`, whose receiver is also a string. **How to prove it wrong.** Already run, no build needed: `RTS_CHAIN_DEBUG=1 target/release/rts.exe run x.ts` on `for (...) a += s16.charCodeAt(i & 15)` prints exactly `rts-chain refused: the receiver has no recorded link`. **What it must survive.** Constraint 2 (conservative stack scan). The cache cell would remember `region.address_of(String.prototype)`; the existing depth-1 argument for that address staying alive is "the receiver's type is discriminated by its link", which text has no link to lean on. Constraint 1 (AOT): nothing about the emitted program changes — the terminator is already emitted at every method callee; only what the resolver answers changes, and it answers the same thing on every run. rts-core rule 10 is not touched: a cache word is not a `Value` and is not scanned. ### A string method resolves its receiver three times; `charCodeAt` already shows what one costs

**Where.** crates/rts-core/src/entry/string/coerce.rs (`coerce_receiver`), crates/rts-core/src/entry/string/mod.rs (`receiver`, `length_of`, `indexed`, `units_of`, `text_of`), crates/rts-core/src/entry/string/basic.rs (`char_at`, `at`, `substring`, and the staged arms of `slice`).

It hands back a VALUE. The method body then takes a second `with_current` and calls `length_of` (which calls `receiver()` and `text_at` again) and `indexed` (which calls `receiver()` and `text_at` a third time). So `"x".charAt(i)` performs three `boxed` probes and three region-plus-slab text resolutions for one immutable string. `char_code_at` is the one method that does not: it was hand-written with a fast arm that reads the cell once under one borrow, and basic.rs's own header records the same lesson for the copy that `units_of` used to make. Expect ~9 ns off `string charAt`-shaped rows and off the staged arms of `slice`, `substring`, `at`, `padStart`/`padEnd`; the fast arms of `slice` and `charCodeAt` already have it and would not move — which is the control.

**How to prove it wrong.** Grep `crates/rts-core/src/entry/string/` for `receiver(` and count the calls reached per method after `coerce_receiver` has already run; `char_at` reaches two (`length_of`, `indexed`) and `char_code_at`'s fast arm reaches none. **What it must survive.** Neither constraint is engaged: no allocation moves, no SSA value changes, the emitted program is identical. The correctness question is entirely local and is the one `coerce_receiver`'s doc already answers — after it returns `Some(held)`, `held` is a bare text cell by construction (it is either the primitive that passed the `text_at` filter, or the freshly interned result of the conversion), so a second `unwrap` cannot change it. The trap to avoid is applying it to the methods that read their receiver BEFORE the prologue (`slice`'s and `char_code_at`'s fast arms take raw `this`); those must keep taking raw `this`, because a wrapper has to fall through to the staged path.

### A dead string pays twenty-one side-table removals for tables it can never be in

**Where.** crates/rts-core/src/entry/collect_cycle.rs (`release`), crates/rts-core/src/heap/aside.rs (`Aside::remove`).

The uncapped half is what matters more: today a `for-of` over a hundred-thousand-element array copies a hundred thousand words and allocates a second array before the first element is seen, and this removes all of it.

**How to prove it wrong.** `cargo run -- ir` on `for (const x of xs)` must show `Call __rts_iterate` in the preheader (already confirmed by reading `emit_source`). For the size without a release build: add a `for-of 256` row beside the existing `for-of 16` and compare per-element figures — if the fixed per-loop cost dominates at 16, the 256 row is sharply lower; if the two are equal, the copy is not what the row is made of and this is worth little.

**What it must survive.** Constraint 2 twice over, and constraint 1 not at all. It removes a region allocation from a preheader, so allocation order moves and the same corpus gate as candidate 1 applies. It is also the only candidate here with a SEMANTIC change: today the copy freezes the element values, so a body writing `xs[j]` for an index it has not reached yet is invisible; walking the source makes it visible, which is what the specification's array iterator does and what Bun and Node answer. That is a change toward the corpus rather than away from it, but it is a change, so `tests/cross-runtime/` has to be compared per file — LOST empty is the claim, and the net number is not.

*Effort: medium.*

### A four-key `Object.keys` builds six vectors and sorts, to answer four numbers the shape already holds in order

**Where.** crates/rts-core/src/entry/array.rs (`key_list`, `ordered_keys`, `interned`); crates/rts-cranelift/src/shape/tree.rs (`ShapeTree::properties`)

**What is there.** `ShapeTree::properties` walks the shape chain pushing into an unreserved `Vec` and then reverses it — it already knows `width(shape)`, so the reallocations are avoidable in one line inside the machine's own file. `key_list` then merges that vector with `ranked_accessors` into a third vector `order`, which for the overwhelmingly common object with no accessors is a copy of the second into a fourth allocation; when `ranked_accessors` is empty the merge can be skipped and the keys pushed straight into a `Vec::with_capacity(width)`. `ordered_keys` then allocates `indices`, `names` and `out`, sorts, and for every name key fetches the key's TEXT and tries to parse it as an array index — while a plain object's four names produce an empty `indices` and an `out` that is `names` again; computing `index_of` once and returning the input untouched when nothing spells an index is exact, not a heuristic. None of this is `Object.keys`-specific: `for-in` runs `key_list` twice per prototype level, and `Object.assign`, object spread, `structuredClone` and `JSON.stringify` all walk the same shape (`json/write.rs` calls `properties` directly).

**What it should be worth.** GUESS. `coll Object.keys 4` reads 142 ns/key and the harness divides by its `ops: 4`, so one `Object.keys({a,b,c,d})` costs ~568 ns. Removing three of the six vector allocations and the sort should be 25-35% of that — 568 → 380-430. The `properties` reservation additionally touches `json stringify small` (1486 ns) and every `for-in`, which nothing in this angle has measured.

**How to prove it wrong.** Cheapest without a build: compare `Object.keys` of a one-key object against a fifteen-key object, per key. The fixed vectors and the sort make the per-key cost FALL as the count rises; the per-key probes (`integrity::enumerable`, `interner.text`, `is_symbol_key`, `key_value`) make it flat. If it is flat, the vectors are not the cost and this candidate is small. The confirming build is an ablation that pushes straight into a reserved vector and returns early from `ordered_keys`; if the row does not move, the premise is refuted.

**What it must survive.** Neither constraint. Every allocation removed is a Rust `Vec` — no `alloc_or_die`, so JS allocation order is unchanged and no root can move. The one thing that must not change is ORDER: integer-spelled keys come first in ascending numeric order and the accessor merge restores insertion order, so the early return from `ordered_keys` has to be conditioned on "no key yielded an index spelling", computed rather than assumed. `rts-cranelift`'s README rules are not engaged by adding a capacity hint to `properties` — it is the same answer, computed from a width the tree already stores.

*Effort: small.*

### Give an array's elements an address the machine can reach from the cell, so `a[i]` stops being a crossing

**Where.** crates/rts-core/src/entry/array.rs (`Context::arrays`, `array_elements`, `elements_at_mut`); crates/rts-core/src/heap/region/mod.rs (a reserved pair of words in the array layout); crates/rts-cranelift/src/ir/inst.rs (`ElementLoad`, and a `CachedElement`-shaped terminator); crates/rts-codegen/src/emit/expr.rs and emit/property.rs (`emit_read_keyed`'s numeric arm)

**What is there.** This answers the survey's first question directly: `array index read` at 13.5 ns is one crossing and nothing else. `emit_read_keyed` deliberately routes a key it has PROVEN numeric straight to `RuntimeOp::GetIndexed` — the keyed cache is skipped because an element is not a property of any layout — so `arr[i & 1023]` is a bare `Call __rts_get_indexed`, and inside it two `with_current` borrows, a proxy probe, `as_index`, two side-table lookups and a hole test. It cannot become an instruction while the elements live in a `Vec<u64>` behind `context.arrays`, reached through the `array_elements` `Aside`. The change is to carry the run's base and length in two reserved words of the array cell, and to emit a terminator that guards the receiver is a reference, loads those two words FROM THE CELL, bounds-checks the index unsigned, loads `base[index]`, and compares against the hole singleton — anything else falling through to today's `GetIndexed` call, exactly as `CachedGet` falls through to `GetProperty`. The base is re-derived from the cell at every access rather than hoisted, which is the whole difference from the design `docs/codegen/element-load.md` reverted.

**What it should be worth.** GUESS, priced off the engine's own precedent rather than measured. A cached own-property read is ~6 ns and this is the same shape — a guard, a load of a header word, a load. `array index read` 13.5 → ~5, `array index write` 14 → ~6, and the `for-of` element (28 today) → ~16 with candidate 3, since `ElementAt` is the other crossing in that loop. It also gives `Inst::ElementLoad` and `TrapCode::OutOfBounds` the client they have never had.

**How to prove it wrong.** Two, both cheap. Mechanism: `cargo run -- ir` on `a[i]` must show a bare `Call __rts_get_indexed` with no guard and no cache — confirmed by reading `emit_read_keyed`'s `Repr::F64 | I32 | I64` arm, which returns before the cache is declared. Design: `grep -rn elements_at_mut crates/rts-core/src` is 25 sites across 17 files, every one of which can grow the run and move its buffer. If those cannot all be routed through a guard type that rewrites the cell's two words on drop, the invariant is unenforceable and the design should die before a line is written — that grep is the go/no-go and costs nothing.

**What it must survive.** Constraint 2 is the whole of this candidate, and the argument has to be made explicitly rather than assumed. The refuted design hoisted the base out of the loop and thereby deleted the last tagged reference to the run's owner; here the base is loaded from the cell inside the same terminator that uses it, with no allocation, no call and no safepoint between the two loads, so no collection can occur while a machine-typed derivative is live — the same argument `entry/cache.rs` makes for a one-step indirect cache. The buffer moving is answered separately, by the drop guard above. The second cost is a design one: the reserved words must not be visible as properties, which means arrays need a private slot pair below the shape's own numbering, and `Object.keys`, `getOwnPropertyNames` and the shape walk must not report them. Constraint 1 is untouched — the terminator is emitted identically on every compile and there is nothing to bail out to.

*Effort: large.*

### A one-cell generator frame can never be reused, and a reused run is not zeroed — `Region::alloc_spanning`

**Where.** crates/rts-core/src/heap/region/span.rs (alloc_spanning, lines 54–94; take_free_run, 100–116), crates/rts-core/src/heap/region/mod.rs (alloc, 502–548; free, 570–620), crates/rts-core/src/entry/alloc.rs (alloc_spanning_or_die, 183–200; grow_if_the_cycle_barely_helped)

**What is there.** `Region::free` splits its answer by width: an object covering ONE cell is threaded onto `free_head` (the cell list), an object covering two or more is pushed onto `free_runs`. `Region::alloc_spanning` reads only `free_runs` (via `take_free_run`) and only after bump space is gone; `Region::alloc` reads only `free_head`. So a spanning allocation whose size rounds to exactly one cell can NEVER come back: it is freed onto a list `alloc_spanning` does not consult, and every new one has to bump `next`. `STRIDE` is 128 bytes (`HeaderLayout::BYTES + 15 * 8`), and the only caller that can ask for one cell is `generator_new` — `objects.rs:79` needs >15 slots and `spill_set`'s `SPILL_CHUNK = 16` both round to 136 bytes, i.e. two cells. A frame for `function* g(){ yield 1 }` is label + resumed + mode + six params + return ≈ 11 words = 88 bytes = one cell. So every small generator permanently consumes fresh bump space; `next` walks to `capacity`, `grow_if_the_cycle_barely_helped` grows on each barren cycle, and the program ends in `heap_exhausted`, whose message is verbatim the symptom recorded as open in `docs/engine/lost-roots.md`. The second half is in the same function: a run taken from `take_free_run` is NOT zeroed — only the first cell's header word is written — while the doc comment says "the rest are zero, as `Self::alloc` leaves them", which is true of bump space and false of a reused run. `State::trace` walks every one of `shape.slots` and offers each word as a root, so a recycled frame hands the marker stale words, and the frame's slot 15 reads `u64::MAX` (FREE_MARKER) where the contract says zero. The fix is one branch each: for `cells == 1` take the same free-list pop `alloc` takes (the header it writes, `header_word(ty, INLINE_SLOTS)`, is bit-identical to `cells * 16 - 1`), and zero the slots of a run that came from `take_free_run` exactly as `alloc` already zeroes a recycled cell.

**What it should be worth.** Not a nanosecond claim. It is the open second symptom of RTS_OPTIMIZATION item 3 — "300 000 rounds exhaust the heap outright, the region grew to its whole reservation of 524288 cells" — and `heap_exhausted`'s text in alloc.rs:262 matches that sentence word for word. The `flow generator next` row (147 ns) would also stop paying a collect-and-grow at the point the bump space runs out, but no number is claimed for that.

**How to prove it wrong.** A `cargo test -p rts-core` unit test on the region alone, no release build, no engine: `Region::with_capacity(2)`, two `alloc_spanning(STRIDE, ty)`, free both, then a third `alloc_spanning(STRIDE, ty)`. It answers `None` today (cells = 1, `1 <= capacity - next` is false, `free_runs` is empty because both frees went to `free_head`). If it answers `Some`, I have misread `free` and the candidate is dead. A second, separate check for whether generators actually reach the one-cell case: print `FrameShape.size` for the `yield 1` repro — if it exceeds 128 the exhaustion has another cause, though the region gap is still real for anything that does fit.

**What it must survive.** Constraint 2, the conservative scan. The one-cell branch changes nothing about what is live where — it changes which free cell is handed out, and `alloc` already hands out recycled cells to everything else in the program. The zeroing half moves in the SAFE direction for the collector: it removes stale words that `State::trace` currently offers as roots, so it can only shrink the retained set, never lose a live reference. Constraint 1 is untouched: allocation order and program identity are unchanged; a deterministic allocator handing back a recycled cell instead of a fresh one is the behaviour `Region::alloc` already has.

*Effort: small.*

### Three avoidable costs inside the Error constructor, all in `written()`

**Where.** crates/rts-core/src/entry/error.rs (written, lines 243–281), crates/rts-core/src/entry/throw.rs (stack_text, 528–551), crates/rts-core/src/entry/context.rs (well_known, 636–695; index_functions_by_code, 526–540)

**What is there.** `try { throw new Error("x") } catch {}` compiles the throw to a plain `jump` — `lower/terminator.rs:210` takes `plan.handler` when the handler is in the same function, so there is no runtime crossing and no unwinding at all. The 1029 ns row is therefore `new Error("x")`, and three of its parts are removable without changing an answer. (a) `stack_text` finds each frame's name with `context.function_names.iter().find(|(at, name, ..)| *at == code && !name.is_empty())` — a linear walk of every function in the PROGRAM, per frame. `Context::function_by_code` already exists and its own documentation says it was built to kill this exact walk in `closure_new`, priced there at 0.42 ns per entry (733.7 ns with two functions against 817.6 with two hundred); `stack_text`, `call_frames` and `function_proto.rs:199` were simply never moved onto it. Extend the derived index — rebuilt in one place from the authority, so no second source — to carry the position in `function_names`, and read the `&str` out of the authority by index. (b) `well_known`'s memo list has "length", "prototype", "value", "done", "next" and nine others, and does NOT have "message" or "stack", so every `new Error` builds both names as UTF-16 and hashes them; the comment there says outright that adding a name "is only ever a speed decision — the answer is identical either way". (c) Line 252 interns the message into a FRESH string cell even when the argument was already a string cell. Strings are immutable and `===` compares text through `same_text`, so handing the existing cell to `put` is unobservable and removes one heap allocation per error.

**What it should be worth.** (a) is READ, not guessed: ~100 functions in `bench/analytic.ts` × 3–4 frames at the throw (`measure` → `timeOnce` → the case arrow) × 0.42 ns ≈ 130–170 ns of the 1029, and it grows with program size rather than with what the program does. (b) and (c) are GUESSES: (c) is one `intern_value`, which this repository prices at 40–90 ns for the allocation alone; (b) is two interns, guess 5–15 ns each. Row: `flow throw+catch`, 1029 ns. Nothing else on the benchmark moves, except that (a) also shortens every `util.getCallSite()` and every uncaught-throw report.

**How to prove it wrong.** One `rts run` on the existing release binary, no rebuild. Add three cases to the analytic harness by hand: `throw 1` caught in the same loop, `new Error("x")` constructed into a sink and not thrown, and `new (class{})()`. If `throw 1` is near `try/catch no throw` at 3.9 and construction is near 1029, the whole row is construction and the target is `written()`. For (a) specifically: run the same `new Error("x")` loop in a file with two functions and in a file with two hundred; if the ns/op does not move with the function count, the linear scan is not the cost and (a) is worth nothing.

**What it must survive.** Neither constraint is engaged for (a) or (b) — a hash lookup replacing a linear one, and a match arm. (c) touches the collector's side: sharing the argument's cell means the error's `message` slot and the caller's string are the same reference, which is strictly FEWER cells to keep alive, and the shared cell is already rooted by whoever passed it. It must not be applied when `to_text` had to CONVERT (`new Error(42)`), which is the `context.text_at(cell).is_some()` test, not a guess about the argument's type.

*Effort: small.*

### `.stack` is rendered and interned on every construction, whether or not anything reads it

**Where.** crates/rts-core/src/entry/error.rs (written, 267–279), crates/rts-core/src/entry/throw.rs (stack_text 528–551, pending 205–225), crates/rts-core/src/entry/accessor.rs, crates/rts-core/src/entry/clone/errors.rs (61, 92)

**What is there.** After candidate 3 has taken the scan out, what is left at every `new Error` is still: a `format!` for the header, a `String` grown one `\n    at name` at a time, a second `format!` joining them, an `intern_value` (a heap cell plus a UTF-8→UTF-16 conversion of the whole trace), an `objects::put` that takes a shape transition on a fresh cell, and a `native::hidden` that allocates the cell's first attributes `Vec`. A program that throws and catches without ever reading `.stack` — which the benchmark row is, and which most `try`/`catch` in real code is — pays all of it. The frames must still be captured AT CONSTRUCTION, which is what makes this not a JIT trick: capture them as the interned name KEYS `Context::described_at` already hands back (numbers, not cells, so nothing new has to be rooted and nothing new has to be traced), record them in an `Aside<Vec<Key>>`, and install `stack` as an own ACCESSOR on the instance whose getter renders, interns, and replaces itself with the own data property. V8 does exactly this, which is why `Object.getOwnPropertyDescriptor(e, "stack")` reporting an accessor before the first read is parity rather than divergence. The two internal readers must go through the same door: `throw::pending` reads `.stack` with `objects::read_property` (which already resolves accessors) and `clone::errors` reads it with `text_at`, which does not — that one is the change's real surface.

**What it should be worth.** A GUESS, and a soft one: 150–300 ns of the 1029 on `flow throw+catch`, from one heap cell (40–90 by this repository's own price), one shape-transitioning `put`, one attributes `Vec`, and three Rust string allocations. It could easily be less, because an own accessor costs an `accessors` Aside write that a data property does not — that trade is the whole risk and it is not priced.

**How to prove it wrong.** Before any of it: in the analytic harness, time `new Error("x")` against `new Error()` with no message and against `new (class{})()`. If `new Error()` — which skips the message branch entirely but still builds the full `.stack` — is not far above the class-instance row at 71–82 ns, the stack write is not where the money is and this candidate dies without a line of code. The confirming measurement is one scratch release build with the `.stack` write deleted outright; if the row does not fall by the estimate, the accessor version cannot recover it either, because it does strictly more work.

**What it must survive.** Constraint 1 is the one to answer, and the answer is that nothing about WHEN is left to run time in a way a program can observe as nondeterminism: the frames are captured at construction as the specification requires, the getter is installed on every error unconditionally, and the same source produces the same program. What is deferred is a string rendering, an ordinary lazy property, not a speculation with a bailout. Constraint 2: the new side table holds interned keys, which are numbers — so it needs no `context_roots` entry and no `trace::edges_of` arm, but it MUST be removed in `collect_cycle::release` beside the other `Aside`s and named in `edges_of`'s closing comment with that reason, which is `rts-core` rule 10 and the discipline `docs/engine/lost-roots.md` check 1 exists to enforce.

*Effort: large.*

### The `{value, done}` an iterator answers is rebuilt from the empty layout on every step

**Where.** crates/rts-core/src/entry/generator/mod.rs (result, 396–408; made, 411–436), crates/rts-core/src/entry/list_iterator.rs, crates/rts-core/src/entry/objects.rs (put, 553+), crates/rts-core/src/entry/context.rs (callable_template / record_callable_template, 480–512)

**What is there.** `generator::result` — shared with `list_iterator`, so it is every step of every stepped iterator in the program — calls `made`, which allocates a plain object at the ROOT shape, then writes `value` and `done` through `objects::put`. Each `put` does an integrity probe, `reconcile_length`, `region.type_of`, `shape_of`, a `slot_of` that misses because the cell is empty, and then a shape transition. The object is always the same two keys in the same order with the same prototype, so the layout it arrives at is one answer for the whole process, recomputed per step. This repository has already solved exactly this shape once and measured it: `Context::callable_template` records the layout the FIRST closure of each form reaches by going through the real `put` path, and later closures are built from the recording — "the two `put`s for `name` and `length` were 78 ns of a 218 ns closure". The same mechanism applies here with one template instead of a table indexed by form, and with the same rule that makes it safe: the template is a recording of what `put` actually did, read back out of the shape, not a second implementation of what `put` would do, so an object built from it is byte-identical to one built the long way and cannot drift the day `put` changes.

**What it should be worth.** A GUESS by analogy with the closure measurement above: 50–80 ns of the 147 ns `flow generator next` row. `array for-of 16` (28 ns) does NOT move — `entry/iterate.rs` materialises an array for arrays and strings precisely so it never builds a result object — so the rows that move are `flow generator next` and any `Map`/`Set`/user-iterator stepping, which the benchmark does not currently isolate.

**How to prove it wrong.** Without a build: in the analytic harness compare `it.next()` on a generator against `map.get(k)` (40 ns, one crossing and no allocation) and against `alloc class instance` (71–82 ns, one allocation with property writes). If `next()` minus a crossing minus an allocation leaves little, the two `put`s are not the cost and the template buys nothing. With a build, the direct check is `RTS_TIMING=1`, which already reports shape/cache activity, on the generator loop before and after.

Measured with target/release/rts.exe on two files identical but for 400 extra compiled-but-never-instantiated functions nested inside an uncalled `pad()`: `new Error()` in a 6-frame stack went 915/995 ns to 1425/1580 ns, i.e. +430 to +585 ns for 400 entries (~0.2 ns per entry per frame, consistent with context.rs's own 0.42 ns/entry figure). An escaping-object-literal control in the same two files read 55-65 ns in BOTH, which is what attributes the delta to the table rather than to GC or allocation. For bench/analytic.ts (~107 function-shaped nodes, ~5 frames at the bench site) that is ~110 ns of the 1029 row, ~10%. The scaling half is the larger argument: a 2000-function program at depth 10 pays ~4 microseconds per Error.

**How to prove it wrong.** Already run, and it is the cheapest one there is: two `rts run`s of the same program, one with N extra never-called nested functions. If the per-Error cost does not grow with the function count, the premise is wrong. Files left at scratchpad/zsmall2.js and zbig2.js. A second, static falsifier: `grep -n 'function_names.iter()' crates/rts-core/src/entry/` must still return throw.rs:517, throw.rs:542 and function_proto.rs:199 — if it returns nothing, someone converted them already.

**What it must survive.** Neither constraint is engaged, which is why this is first. It emits no code, so AOT determinism is untouched; it allocates nothing new and introduces no heap reference (the interner owns the text and roots.rs:96 already lists `function_names` as non-Value), so the conservative scan sees the same words. The one thing to verify rather than assume is behaviour, not speed: `rts-host/tests/running.rs::an_error_says_where_it_came_from` asserts both that a throwing frame IS named and that two inlined frames are ABSENT, so the empty-name filter must survive the move from `String::is_empty` to a check on the interned key's text.

*Effort: small.*

### The `flow throw+catch` row is 99% `new Error()` and 1% throw — and nothing on the list looks at the constructor

**Where.** crates/rts-core/src/entry/error.rs:232-278 (`written`); crates/rts-core/src/entry/context.rs:636-680 (`well_known`'s memo list) and :554-580 (`intern_value`); crates/rts-core/src/entry/native.rs:95 -> integrity.rs `set_attributes`.

**What is there.** Measured decomposition of the row: `throw "x"` caught in the same loop costs 10 ns; `new Error("x")` with no throw at all costs 1170; `new Error()` with no message costs 850. So the throw/catch machinery is free and the row is the constructor. `written()` does, per construction: (a) `context.well_known("message")` and `well_known("stack")` — neither string is on the twenty-name memo list at context.rs:650-670, so both fall through to `Str::from_str` (a fresh UTF-16 buffer) plus a full interner hash and probe, twice, for two names that cannot change; (b) `intern_value(Str::from_str(&stack))`, and `intern_value` (context.rs:554) allocates a region cell AND a slab entry every call with no dedup, so the identical stack text mints a fresh string cell on every Error — the same defect plan.md L1(c) already records for `closure_new`'s `.name`, unfixed here; (c) `native::hidden` twice, which reaches `integrity::set_attributes` and materialises the per-cell attribute `Aside` — the same write the array-`length` work measured at 84 ns of a 136 ns `[]` (integrity.rs:120-140) before deriving it instead. Three allocations and two interner misses per Error, none of them carrying information that varies.

**What it should be worth.** The fixed cost is READ at 915-995 ns per `new Error()` (release binary, min of 7, 200 000 iterations, stack depth ~6), and it is ~90% of the `flow throw+catch 1029` row. Which of the three mechanisms owns how much of it is NOT decomposed and I will not pretend otherwise — GUESSED split, by analogy with numbers already in the tree: 3 allocations at the repository's own 40-90 ns each is 120-270, the attribute record is ~84 by the array-`length` precedent, two `well_known` misses maybe 40-60. That leaves a residual nobody has named, which is exactly why the first step is an ablation and not a patch.

**How to prove it wrong.** An ablation inside one binary, in the order the tree already uses for this: add `"message"` and `"stack"` to `well_known`'s match, measure; then short-circuit the `.stack` write entirely (temporarily, not shippable) and measure. If suppressing the whole `.stack` write does not move 915 ns by more than ~150, the stack half is not where it is and the target is the object construction. Cheapest static check first: `grep -n '"message"\|"stack"' crates/rts-core/src/entry/context.rs` must return nothing inside `well_known`.

**What it must survive.** Constraint 2, directly and seriously. Removing or reordering the two `intern_value` allocations changes allocation ORDER inside a function that is already known to need explicit rooting — `error.rs:212` wraps AggregateError's list in `super::rooted::Rooted` for exactly this reason, and docs/engine/lost-roots.md records a case where one `eprintln!` inside `collect` changed a program's answer. So any memoising of the stack cell must be rooted where the scan reaches it, and the four checks in lost-roots.md are the gate, not the test suite. Constraint 1 is not engaged: nothing here is deferred or speculative, the same work happens in the same order on every build.

*Effort: medium.*

### `c ? a : b` costs 2.33 ns more than the identical `if`/`else`, because one merge hardcodes UNPROVEN where its own sibling reads the representation

**Where.** crates/rts-codegen/src/emit/choice.rs:57-90 (`merge`); crates/rts-codegen/src/emit/merge.rs:44-68 (`parameters`, which already implements the right rule); crates/rts-codegen/src/emit/proven.rs:806-823 (the `ExprKind::Conditional` arm).

**What is there.** `choice::merge` creates the join with `builder.add_block_param(join, UNPROVEN)` and then calls `builder.widen(path.value)` on both arms, unconditionally — the comment says two paths can produce two representations and there is no third that is both. That is true in general and false in the case that matters. Its own neighbour `merge::parameters`, used in the same function for the disagreeing BINDINGS, does the opposite: it reads `builder.repr_of(reference[position])` and gives the join a parameter at the representation that arrives. Applying that rule to the value slot when and only when both arms already carry the same non-reference `Repr` (F64 or Bool) removes both widens and lets `proven.rs`'s `Conditional` arm — which is `false` today and whose comment names this exact emission change as its precondition — become `is_numeric(then) && is_numeric(else)`. `if`/`else` is the control: it goes through `emit_if`, which uses `merge::parameters`, and it keeps the proof today.

**What it should be worth.** READ, 2.33 ns per `?:` evaluation. Release binary, 3 000 000 iterations, min of 7: `a = i > 3 ? a + 1 : a + 2` in a loop is 3.67 ns/iteration; the byte-for-byte equivalent `if (i > 3) { a = a + 1 } else { a = a + 2 }` is 1.33, which is exactly the plain `a = a + 1` floor. `rts ir` on the ternary shows `Widen` on both arms and a guarded arithmetic path afterwards. There is NO row for this in the benchmark table, and I did not find an amplification: a second probe where the `?:` result feeds three more operators measured 6.67 against 7.33 for the `if` form, so the 'the whole loop falls off the proven path' story is REFUTED and the honest claim is the flat 2.33 ns per site.

**How to prove it wrong.** One `rts ir` and no build: the two functions in scratchpad/zcond.ts must differ, with `Widen` on the ternary's arms and none on the `if`'s. If they emit the same IR the premise is gone. Then the timing pair above, which needs only `rts run`.

**What it must survive.** Constraint 2 is the one to be careful with, and it decides the shape of the rule. Taking the arms' representation for the join parameter changes which SSA values are live in which representation — and a REFERENCE narrowed into a join parameter is precisely the 'machine-typed derivative of a heap reference is invisible to a conservative collector' class that docs/codegen/element-load.md says kills this whole family. So the admission must be an allow-list of non-reference reprs (F64, Bool), never `Repr::Ref`, and never 'whatever `repr_of` answers'. Constraint 1 is untouched: both arms' representations are known at compile time, so the same source emits the same program every build. Rule 5 of rts-codegen's README is respected — this widens the set of things that ARE proven, it does not claim a proof for something generic.

*Effort: small.*

### Every function activation calls `__rts_thrown_address` — a runtime crossing for a per-run constant the machine already knows how to import

**Where.** crates/rts-codegen/src/emit/function.rs:945-978 (the unconditional entry-block call); crates/rts-codegen/src/runtime/mod.rs:366-386 (`RuntimeOp::ThrownAddress`); crates/rts-core/src/entry/current.rs:126-142 (`thrown_address`); the mechanism it should use is crates/rts-cranelift/src/mem/address.rs:67 (`RegionBases`, `RegionBase::Symbol`/`Immediate`) and mem/imports.rs:35 (`HeapImports`).

**What is there.** `emit_body_into` opens the entry block of EVERY non-suspending function with `Call { callee: __rts_thrown_address }`, and the comment says why: whether the body will check is not known until it has been emitted, so the address is asked unconditionally — 'a call per activation to save one per operation'. Confirmed by `rts ir` on a three-function file: block0 of all three begins with `v6: I64 = Call { callee: FuncId(1), args: [] }`. But the value is a thread-local address that is constant for the life of the thread, which is the same shape of fact as the heap base — and the machine already has a mechanism for exactly that: `RegionBase::Immediate` for a JIT that compiles in the process that runs, `RegionBase::Symbol` plus `HeapImports` for an object file that does not. current.rs's stated objection ('a data symbol is shared between threads while this word is not') is one this engine has already accepted for the region base, and it cannot bite today because nothing here runs JavaScript on two threads (CLAUDE.md removed the `thread` namespace for that reason). The language-layer fallback for a body with no address (`ctx.body.flag == None` -> call `RuntimeOp::Thrown` at the site) already exists, so correctness never depended on the entry call.

**What it should be worth.** GUESSED which end of a read range. docs/codegen/entry-tax.md gives two instruments: a crossing with a trivial body is 3.10 ns in `bench/isolated/src/bin/crossing_price.rs`, and 13.8 ns per crossing measured in-engine with intercept zero. `__rts_thrown_address` takes no arguments, returns an I64, does no `with_current` and does not box, so 3-5 ns is the likelier end. Row: it is paid by every activation, so `alloc class instance 71-82` (the constructor body of `class Callee { v: number = 1 }` is one activation) and every row containing a real JS call. I could not isolate it from JavaScript, and I am not going to claim a row number I did not read.

**How to prove it wrong.** Two, both cheap. Static: `rts ir` on any file must show `Call FuncId(1) __rts_thrown_address` as the first instruction of block0 in every function — already run, it does. Priced: run the existing `bench/isolated/src/bin/crossing_price.rs` and read its trivial-body row; if a zero-argument crossing is under ~2 ns, the whole item is worth less than the machine change costs and should be dropped before anything is written. Third, decisive and still cheap: build once with the entry call suppressed and the site fallback (`RuntimeOp::Thrown`) taking over, and measure a real-call row. If it does not move, the premise is wrong.

**What it must survive.** Constraint 2, and it is the reason this is last rather than first. Deleting a call from every entry block changes what the register allocator spills across the rest of the function, and this collector finds roots in compiled frames by bit pattern from a conservative stack scan — a reference that used to be spilled because a call clobbered its register may now stay in one the scan does not read. That is the same class as the egraph knob refuted 3/3, arriving from a different direction, and it must be gated on the four checks in docs/engine/lost-roots.md rather than on a green suite. Constraint 1 is fine: the address is imported the same way on every build, nothing is deferred, and the JIT/AOT split is already the difference `RegionBase` exists to express. Architecture: the classification stays in the language layer (which `RuntimeOp` this replaces), the address import is a machine question, so nothing crosses.

*Effort: large.*

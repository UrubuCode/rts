# 04 — Precedent: how Bun and Deno implemented N-API

> The roadmap RTS would follow. Bun (on top of JavaScriptCore, **not** V8) is the
> closest precedent to RTS; Deno (on top of real V8) shows the contrast.
> Verified against Bun's blog/docs, `deno_napi`, and GitHub issues.

## 4.1 The contract is identical for both: `napi_register_module_v1`

Both load the `.node` via `dlopen`/`libloading`, resolve
`napi_register_module_v1(napi_env, napi_value exports) -> napi_value`, fabricate
a `napi_env`, create an empty `exports`, and call the init. The error when the
symbol is missing (seen in non-Node runtimes):
> `symbol napi_register_module_v1 not found in native module. Is this a Node API (napi) module?`

## 4.2 Deno — the "easy" path (V8 engine)

- Embeds V8 via **rusty_v8**; hence `napi_value` **is** a real `v8::Local` —
  **no engine translation**. `deno_napi` only does transmute/abstraction.
- Structure: `deno_napi` crate with `Env`, `EnvShared`, `NapiModule`, `NapiState`,
  `InstanceData`; modules `js_native_api` (value operations), `node_api`,
  `function`, `value`, `uv` (libuv integration).
- Symbols: `#[napi_sym::napi_sym]` macro, names in
  `cli/napi_sym/symbol_exports.json`, `.def` generated by
  `tools/napi/generate_symbols_lists.js`. Loader via `libloading`
  (`DenoRtNativeAddonLoader`).
- **Permission model:** addons require a local `node_modules/` + the
  **`--allow-ffi`** flag (same permission as raw FFI, since it runs outside the
  sandbox; accepts a path list `--allow-ffi=./libfoo.so`).
- **`deno compile`:** historically failed with addons (issue `#23266`,
  `LoadLibraryExW failed`). PR `#28934` added
  `deno_rt_native_addon_loader` which **extracts** the embedded shared libs /
  `.node` **to a temp file** and opens them from there (self-extracting model).
  Admitted limitations: does not work on a read-only FS nor if the lib needs
  other real files on disk.

> **Verified nuance (`napi_value` in Deno):** it is not *literally* a
> `v8::Local`. In `ext/napi/value.rs` it is a newtype
> `#[repr(transparent)] NapiValue<'s>(Option<NonNull<v8::Value>>)` —
> **nullable** (≠ rusty_v8's non-nullable `Local`), convertible to/from
> `v8::Local` via `From` and `Deref`/`transmute` **with no engine translation**
> (because the engine *is* V8). A near-zero-cost bridge, cheaper than Bun's.
> The `deno compile --self-extracting` flag (validated on Deno 2.3) is the AOT
> mechanism.

**Lesson for RTS:** Deno had the easy path for `napi_value` (it has V8). RTS is
**not** on that path — it follows the **Bun** model (map `napi_value` to its own
handle). But the **permission model** (`--allow-ffi`) and the **self-extracting
model** for AOT are directly reusable.

## 4.3 Bun — RTS's path (non-V8 engine)

- Uses **JavaScriptCore**; treats `napi_value` as a `JSC::JSValue`
  (`EncodedJSValue`, 8 bytes, **NaN-boxing**, ≠ V8's tagged pointer), via
  `reinterpret_cast` + `JSValue::encode/decode`. JSC's NaN-boxing uses a
  **16-bit upper tag** (not "2 bits"): tag `0x0000` = 48-bit `JSCell`
  pointer (heap objects); tag `0xFFFE` = signed `int32` (e.g.
  `0xfffe000000000000 | (uint32_t)input`).
- **COMPLETE surface coverage:** issue `oven-sh/bun#158` reports
  **156/156** `napi_*`/`node_api_*` functions implemented and exported. The
  remainder is **behavioral parity (~95%)**, not missing API.
- Runs Node's official suites in CI: `js-native-api` (engine-agnostic,
  ~98-100%), `node-api` (Node-specific, ~48%), combined ~76%.
- Code structure (**current** repo paths — a template for RTS):
  - `src/jsc/bindings/napi.cpp` — `napi_*` functions + JSC integration (values);
  - `src/runtime/napi/napi.zig` — threadsafe functions, async work, event loop,
    handle scopes;
  - `src/jsc/bindings/v8/` — shim of V8's C++ ABI (for NAN addons);
  - `src/symbols.txt` — list of exported symbols.
  > (Old paths `src/bun.js/bindings/...` appear in dated material.)

### How Bun manages handle scopes (a direct model for RTS)

A 24-byte stack-allocated `HandleScope` { Isolate ptr, previous-scope ptr,
`HandleScopeBuffer` ptr }; in the constructor it marks itself as *current*, in
the destructor it restores the previous one. The current scope lives in
`globalObject->V8GlobalInternals()->currentHandleScope()` (lazily hung on the
global object). Each `Handle` = 24 bytes. The returned `napi_value` is a pointer
to the **stable** slot in the buffer — **never** the object's pointer directly.

**Critical lesson for RTS:** `napi_value` must be a **stable indirection**
(a slot in the `HandleTable`/handle scope), never the raw pointer of a
`RuntimeValue` — otherwise RTS's mark+sweep can collect/invalidate the value in
the middle of the native call (the "handle collected before use" class of bug
RTS has already documented).

> **Verified nuance (why Bun's naive implementation fails):** JSC's GC is
> **non-moving** (Riptide, non-compacting — `JSCell`s stay at a fixed address),
> so the problem is **not** a pointer invalidated by a moving collection. The
> naive implementation (parts 1-2 of the blog) is "deeply broken" because the
> `Handle`s live in a `HandleScopeBuffer` that JSC's collector does **not
> track** — objects referenced only by handles can be collected while still
> live (a **rooting/GC-visibility** problem, not a movement one). It is exactly
> the analogous risk in RTS: the handle scope must be registered as a
> **scannable root** by `mark_stack_roots()`, otherwise the sweep collects what
> the addon is still using. RTS's non-moving GC (like JSC's) eases the *address
> stability* part, but does **not** waive the rooting.

### The hard step Bun does not fully cross

- **async_hooks** not integrated (Bun recommends `AsyncLocalStorage`);
- **libuv:** only a **subset** of `uv_*` symbols exported;
  `uv_default_loop()` ≠ the runtime's loop → addons that use it directly break;
- finalizer ordering on *worker terminate* diverges;
- `napi_adjust_external_memory` differs from V8.

### The V8-C++ shim (NAN) — a separate project, years of work

Issue `oven-sh/bun#4290`: for NAN/direct-V8, Bun shimmed (since **v1.1.25**,
Aug/2024) `v8::Isolate::GetCurrent`, `HandleScope`, `EscapableHandleScope`,
`Number/String/Boolean/Object/Array/External`, `FunctionTemplate`,
`ObjectTemplate`, internal fields, `node_module_register`, cleanup hooks.
**Still broken:** advanced Array operations, `ObjectTemplate` with constructors,
`FunctionTemplate` cases, `ArrayBuffer`, UTF-16 strings, persistent handles. The
naive attempt to reinterpret `Local<T>` ↔ `JSValue` **failed** because V8's
inline functions dereference assuming the V8 layout.

## 4.4 Compatibility map of real addons (test baseline)

| Addon | Bun | Deno | Why |
|---|---|---|---|
| `esbuild` | ✅ | ✅ | pure N-API |
| `sqlite3` (npm) / `duckdb` | ✅ | ✅ | N-API |
| `better-sqlite3` | ⚠️ worked around via `bun:sqlite` | ❌ (`#18444`, can't find bindings) | native addon; Deno uses `libsql`/`denodrivers` |
| `sharp` | ✅ (libvips + WASM fallback, 2026) | partial | N-API + binary |
| `bcrypt` | ✅ (N-API since v4.0.0; Bun v1.0.19+) | partial | migrated V8-C++ → N-API; `bcryptjs`/`Bun.password` remain as convenience |
| `node-canvas` (v2) | ❌ | ❌ | V8-C++ |

> **Verified nuance (2025-2026 state):** `bcrypt` is **no longer** "V8-C++ that
> breaks" — it migrated to N-API in v4.0.0 and Bun v1.0.19 unlocked official
> support. The canonical example of "breaks due to direct V8-C++" is
> `node-canvas` (v2). `better-sqlite3` is a native addon but the friction in
> Deno is failing to find the bindings file, not V8-C++.

**General pattern:** **pure N-API** addons tend to work; addons using
**nan/v8.h directly** break in both runtimes — confirming the boundary RTS
should adopt.

**"Built-in API instead of addon" strategy:** Bun offers `bun:sqlite`
(4-6× faster than `better-sqlite3`, avoids N-API marshaling). RTS already has
native namespaces (`crypto`, `net`, future `sqlite`?) that can serve as an
alternative when the N-API addon is infeasible.

## 4.5 Effort estimate (from the precedent)

- **Bun:** "complete" N-API surface (156/156 fns in issue #158's count),
  but **behavioral parity +
  V8-C++ shim** consumed releases from v1.1.25 (Aug/2024) to today, with **three
  blog posts** just explaining the layout emulation. Combined still **76%** on
  Node's suites.
- **Deno:** `napi_sym` macro + JSON symbol list; **stable** support in
  Deno 2.0; clean organization (`js_native_api.rs`/`node_api.rs`/`function.rs`/
  `value.rs`/`uv.rs`).

**Order of magnitude for RTS:** the full Strategy A (the whole N-API) is
**many months**. But the **80/20 core** (~40 synchronous fns) runs most simple
N-API addons and is much smaller — see [`06-estrategia-roadmap.md`](06-estrategia-roadmap.md).

## Chapter conclusion

- RTS follows the **Bun template** (non-V8 engine → map `napi_value` to its own
  handle), with Deno's code organization (declarative symbol list).
- `napi_value` = **stable indirection** (handle), never a raw pointer — aligned
  with RTS's `HandleTable`.
- Realistic scope = **pure N-API**; V8-C++/NAN out (the boundary neither Bun nor
  Deno fully crosses).
- Test baseline ready: `esbuild`, `sqlite3`, `sharp` (yes); `bcrypt`,
  `better-sqlite3`, `canvas` (no) — useful to measure parity, as RTS already
  does with cross-runtime fixtures.

Design: .rtslib as an external namespace

  What a .rtslib would be

  A container file (tar.gz or renamed zip) with:

  ssh2.rtslib
  ├── manifest.json                     — metadata: namespace, version, callees, ABI version
  ├── x86_64-pc-windows-msvc/
  │   └── ssh2_namespace.o              — object compiled for the target
  ├── x86_64-unknown-linux-gnu/
  │   └── ssh2_namespace.o
  ├── aarch64-apple-darwin/
  │   └── ssh2_namespace.o
  └── types/
      └── ssh2.d.ts                      — TS types generated by the crate

  manifest.json:
  {
    "schema": 1,
    "namespace": "ssh2",
    "version": "0.1.0",
    "rts_abi_version": 1,
    "callees": ["ssh2.connect", "ssh2.exec", "ssh2.close"],
    "targets": ["x86_64-pc-windows-msvc", "x86_64-unknown-linux-gnu"]
  }

  ---
  The rts_namespace crate (proc-macro)

  The .rtslib author writes pure Rust with the macro — without needing to know the RTS internals:

  // Cargo.toml of the user's crate
  // [dependencies]
  // rts_namespace = "0.1"

  use rts_namespace::namespace;

  #[namespace(name = "ssh2")]
  mod ssh {
      use rts_namespace::prelude::*;

      /// Opens an SSH connection. Returns a session handle.
      #[callee("ssh2.connect")]
      pub fn connect(
          host: StrArg,   // (ptr: i64, len: i64) — RTS convention
          port: i64,
      ) -> u64 {           // opaque handle
          // real implementation with the ssh2 crate from crates.io
          todo!()
      }

      /// Executes a command on a session handle.
      #[callee("ssh2.exec")]
      pub fn exec(session: u64, cmd: StrArg) -> StrHandle {
          todo!()
      }
  }

  The macro automatically generates:
  - #[unsafe(no_mangle)] pub extern "C" fn __rts_ssh2_connect(ptr: i64, len: i64, port: i64) -> u64
  - pub const SPEC: NamespaceSpec
  - pub const MEMBERS: &[NamespaceMember]
  - The .d.ts as an embedded string (via include_str! of a file generated in build.rs)

  The .o is generated with cargo build --release targeting each triple. Packaging into .rtslib would be via an auxiliary CLI rts_namespace pack.

  ---
  Pipeline integration

  package.json of the user's project:
  {
    "name": "meu-app",
    "rtslibs": [
      "https://raw.githubusercontent.com/.../ssh2.rtslib",
      "./libs/meu_custom.rtslib"
    ]
  }

  During rts run / rts compile:

  1. Reads rtslibs from package.json
  2. Downloads and verifies SHA256 (hash declared in the manifest)
  3. Extracts and caches into node_modules/.rts/libs/<namespace>/
  4. Selects the .o for the current target triple
  5. Injects the .d.ts into node_modules/.rts/builtin/<namespace>/
  6. Registers the manifest's callees in NamespaceUsage — the linker includes the .o together with the other namespace objects

  The import "rts:ssh2" or "ssh2" resolves to the generated .d.ts, exactly like "rts:fs".

  ---
  Where this differs from Node's .node

  ┌───────────────┬─────────────────────────────┬────────────────────────────────────────┐
  │               │       .node (Node.js)       │             .rtslib (RTS)              │
  ├───────────────┼─────────────────────────────┼────────────────────────────────────────┤
  │ Loading       │ dlopen at runtime           │ static linkage at compile time         │
  ├───────────────┼─────────────────────────────┼────────────────────────────────────────┤
  │ ABI           │ N-API (V8 types)            │ pure machine types (i64, f64, u64)     │
  ├───────────────┼─────────────────────────────┼────────────────────────────────────────┤
  │ Overhead      │ indirect call via N-API     │ zero — direct symbol in the binary     │
  ├───────────────┼─────────────────────────────┼────────────────────────────────────────┤
  │ Portability   │ .node per platform          │ .o per triple in the container         │
  ├───────────────┼─────────────────────────────┼────────────────────────────────────────┤
  │ Security      │ dlopen opens at any time    │ link time — hash verified beforehand   │
  └───────────────┴─────────────────────────────┴────────────────────────────────────────┘

  The .rtslib is more like a precompiled static crate with namespace metadata than a dynamic addon. The final binary has no dynamic-loading dependency whatsoever.

  ---
  Security considerations

  - The manifest.json declares an rts_abi_version — RTS refuses a .rtslib with an incompatible ABI version
  - SHA256 hash of the file declared in package.json or in a .rtslibs.lock lockfile (analogous to bun.lock)
  - .rtslib from a URL without a declared hash → warning or error depending on the profile

  ---
  Current feasibility

  What already exists and serves as a base:
  - emit_selected_namespace_objects() already iterates over objects and passes them to the linker — adding .rtslib objects is trivial here
  - NamespaceUsage already tracks callees per source — the .rtslib manifest feeds this directly
  - ObjectCacheMeta / is_cached_object_valid — the .o cache already exists, it just needs a variant for .rtslib

  What would need to be created from scratch:
  - The rts_namespace crate (proc-macro + runtime types)
  - The .rtslib packaging format (simple zip with manifest)
  - rts_namespace pack (CLI to package multi-target)
  - Resolution of rtslibs in package.json
  - Hash verification and lockfile

  The idea is architecturally sound and breaks no existing invariant — the .rtslib is just one more .o for the linker, with extra metadata so RTS knows which callees it exposes.

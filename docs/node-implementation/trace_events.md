## 1. Purpose

`node:trace_events` is a small control-plane API for Node's process-wide tracing
subsystem: it lets userspace code turn specific **trace event categories**
on/off at runtime (in addition to whatever categories were requested via the
`--trace-event-categories` CLI flag) and query the currently-effective set.
The subsystem itself centralizes structured, timestamped instrumentation data
generated by V8 (GC, compilation, execution), Node's own core modules
(bootstrap milestones, fs/dns/net/http/threadpool/promise/module-loader
events), and optionally userspace code, writing it to a rotating log file in
the Chrome/V8 JSON "Trace Event Format" so it can be opened and visualized in
`chrome://tracing` or any compatible viewer (Perfetto, etc.). The module's own
JS-visible surface (`Tracing` class + two functions) is deliberately tiny; the
overwhelming majority of the "feature" is the *producers* — the dozens of
internal instrumentation points scattered across V8 and Node core that only
fire when their category is enabled.

## 2. Exported API surface (COMPLETE)

### 2.1 Classes

#### `class Tracing`

*Added: v10.0.0.* Not constructible by user code — instances are obtained
exclusively from `trace_events.createTracing()`. Represents one **named set of
categories** the caller wants to control together as a unit; multiple
`Tracing` objects may cover overlapping categories (see §4 for the union/
ref-count semantics this implies).

- **Instance properties**

  | Property | Type | Description |
  |---|---|---|
  | `tracing.categories` | `string` (readonly) | A comma-separated list of the trace event categories covered by this `Tracing` object (the same set passed to `createTracing({ categories })`, joined). |
  | `tracing.enabled` | `boolean` (readonly) | `true` only if `tracing.enable()` has been called on **this** object and not yet followed by a matching `tracing.disable()`. Newly-created `Tracing` objects are always `enabled === false`. |

- **Instance methods**

  ##### `tracing.enable()`

  No parameters. Returns `undefined`. Throws: never. Variant: **sync**.
  Adds every category in `tracing.categories` to the process-wide enabled set
  (creating it, if this is the first `Tracing`/CLI source to request it).
  Idempotent in effect (calling twice while already enabled does not
  double-count — see §4) though it is *not* documented as returning any
  chainable value (unlike `AsyncHook#enable()` in `node:async_hooks`, this
  returns `undefined`, not `this`).

  ##### `tracing.disable()`

  No parameters. Returns `undefined`. Throws: never. Variant: **sync**.
  Removes every category in `tracing.categories` from the process-wide
  enabled set — **except** any category that is still covered by (a) another
  currently-`enabled` `Tracing` object, or (b) the `--trace-event-categories`
  CLI flag. Those categories remain enabled; only categories exclusively held
  by this `Tracing` object actually stop being captured.

### 2.2 Top-level functions

##### `trace_events.createTracing(options)`

*Added: v10.0.0.*

| Param | Type | Optional | Default |
|---|---|---|---|
| `options` | `{ categories: string[] }` | no | — |
| `options.categories` | `string[]` | no | — |

Returns: `Tracing`. Throws: an error (documented informally as "an error will
be thrown") if any element of `options.categories` cannot be coerced to a
`string` — every element that *can* be coerced (numbers, etc.) is coerced
silently. Variant: **sync**. Creates and returns a new, initially-**disabled**
`Tracing` object for the given category set. Creating the object has no
observable side effect on the enabled set until `.enable()` is called.

##### `trace_events.getEnabledCategories()`

*Added: v10.0.0.* No parameters.

Returns: `string` — a comma-separated list of **all** currently-enabled trace
event categories, deduplicated, computed as the **union** of every currently-
`enabled` `Tracing` object's categories plus every category named by the
`--trace-event-categories` CLI flag. Returns an empty string `""` when nothing
is enabled (verify exact empty-case return — may be `undefined` in some Node
versions; treat `""` as the target for RTS regardless, see §7). Throws: never.
Variant: **sync**.

**Default-enabled categories:** `node`, `node.async_hooks`, `v8` — this is
the set activated when the tracing subsystem is turned on from the CLI via
`--trace-events-enabled` with **no** explicit `--trace-event-categories`
value (verify exact CLI flag interaction text, §7); it is *not* a JS-level
default (a freshly-started process with no CLI tracing flags at all and no
`createTracing().enable()` call has an **empty** enabled set —
`getEnabledCategories()` returns `""`).

**Trace file naming** (not a JS export, but part of the module's documented
contract): default `node_trace.${rotation}.log`, where `${rotation}` is an
incrementing rotation id; customizable via the CLI flag
`--trace-event-file-pattern '<pattern>'` supporting `${rotation}` and `${pid}`
placeholders. Output is the Chrome/V8 JSON "Trace Event Format", openable in
`chrome://tracing`. See §3/§4 for the record schema and rotation/timestamp
details.

### 2.4 Events

Neither `Tracing` nor the module itself is an `EventEmitter` — there is no
`on`/`emit`/`once`. The only "event"-shaped concept in this module's public
surface is the **trace record** written to the log file once a category is
enabled and a producer somewhere in the process fires — see §3
(`TraceEventRecord`) for the full field schema. There is no way to observe
these records from JS at runtime (no in-process subscriber API exists in real
Node for this module — that role is filled by the unrelated
`node:diagnostics_channel` module for structured pub/sub, and by
`node:perf_hooks`'s `PerformanceObserver` for a JS-visible subset of `node.perf`
data); trace records are only observable by reading the emitted log file
after the fact.

**Availability note:** *the features from this module are not available in
`Worker` threads* — stated verbatim in the Node docs. See §4/§5.4 for what
this implies for RTS.

```ts
 * One record in the emitted trace log — the Chrome/V8 JSON "Trace Event
 * Format" (a documented open format, not V8-proprietary). RTS's own writer
 * targets this same shape for viewer compatibility (chrome://tracing).
 * Field names follow the format's established abbreviations.
 */
interface TraceEventRecord {
  /** Event name (free text, e.g. "V8.GCScavenger", "fs.readFileSync"). */
  name: string;
  /** Category (comma-joined if the producer tags multiple at once). */
  cat: string;
  /**
   * Phase: 'B'/'E' (duration begin/end), 'X' (complete, has `dur`),
   * 'I' or 'i' (instant), 'C' (counter), 'b'/'e'/'n' (nestable async
   * begin/end/instant), 'M' (metadata, e.g. process/thread names).
   */
  ph: "B" | "E" | "X" | "I" | "i" | "C" | "b" | "e" | "n" | "M";
  /** Timestamp in microseconds, same clock source as process.hrtime(). */
  ts: number;
  /** Thread-clock timestamp in microseconds (optional, often omitted). */
  tts?: number;
  /** Process id. */
  pid: number;
  /** Thread id (OS thread id, or a stable synthetic id per RTS thread). */
  tid: number;
  /** Duration in microseconds — required when ph === "X". */
  dur?: number;
  /** Async/nestable-event correlation id — required when ph is b/e/n. */
  id?: string;
  /** Event scope for async ids ('g' global / 'p' process / 't' thread). */
  s?: "g" | "p" | "t";
  /** Free-form structured payload (producer-defined, JSON-serializable). */
  args?: Record<string, unknown>;
}

/** Shape of the file this module writes (Chrome Trace Event Format, "JSON Array Format" variant). */
interface TraceEventLogFile {
  traceEvents: TraceEventRecord[];
  /** Optional format metadata some viewers read (displayTimeUnit, etc.) — not required. */
  [metaKey: string]: unknown;
}
```

## 4. Node semantics & edge cases

- **Category enable/disable is reference-counted across sources, not a
  simple boolean.** `getEnabledCategories()` is defined as the *union* of (a)
  every currently-`enabled` `Tracing` object's `categories`, and (b) the
  `--trace-event-categories` CLI flag's list. Calling `disable()` on one
  `Tracing` object only removes categories that are **exclusively** held by
  that object — a category still requested by another enabled `Tracing`
  object or by the CLI flag stays enabled. The CLI flag's categories can
  never be turned off from JS at all (there is no API to mutate the CLI-
  supplied floor).
- **A `Tracing` object's own `enabled` boolean guards against double-counting.**
  A conforming implementation must not increment the same category's
  reference count twice for one `Tracing` object across two `enable()` calls
  without an intervening `disable()` — otherwise a single `disable()}` would
  under-decrement and leak the category enabled forever. (Node's own
  behavior here is implied by the property semantics, not spelled out
  operationally in prose; RTS must get this right regardless — see §5.1.)
- **`createTracing()` has no side effect until `.enable()` is called** —
  constructing the object does not touch the global enabled set.
- **Category values are coerced to string; non-coercible values throw** —
  e.g. `createTracing({ categories: [{}] })` (an object with no meaningful
  `toString`) is documented to throw; primitives coercible via `String(x)`
  (numbers, `null`, `undefined` → `"null"`/`"undefined"` strings, etc.) do not.
- **`node` is a no-op placeholder category** — enabling it alone produces no
  events; it exists so the default-enabled set has *some* baseline entry and
  so future generic Node-level events have a home without a version bump to
  every other category name.
- **The tracing subsystem itself is lazily activated.** Nothing is written to
  disk until at least one category becomes enabled (via CLI flag or the JS
  API) — merely `import`-ing the module and never calling `createTracing()`/
  `.enable()` produces zero trace file, zero overhead beyond the category-
  registry lookups every producer call site performs (a cheap set/hashmap
  membership check gated before any event-payload construction — see the
  `hasSubscribers`-style fast-path discipline that this module's producers
  must also follow, even though there is no public `hasSubscribers`-shaped
  function exposed for this module specifically).
- **Timestamps use the `process.hrtime()` clock, in microseconds** (not
  nanoseconds like `process.hrtime()` itself returns) — a monotonic,
  not-wall-clock source. All records in one process share one clock origin,
  so relative ordering/duration math across records is meaningful even
  across threads.
- **File rotation.** The default filename embeds an incrementing
  `${rotation}` id; the exact trigger for bumping it (event count threshold?
  byte-size threshold? one rotation per V8 "trace buffer" flush?) is not
  spelled out in the public docs — verify against Node/V8 source before
  implementing a byte-identical policy; RTS's own policy (§5.1) need not be
  byte-identical, only "a monotonically increasing rotation id in the
  filename", which is the only externally observable contract.
- **Not available inside a `Worker` thread at all.** The public docs state
  this as a flat limitation with no further nuance (does `require`/`import`
  throw, or silently return an inert module whose functions are no-ops?) —
  verify exact behavior against Node source; RTS should pick one and
  document the choice explicitly rather than leaving it ambiguous (see §7).
  Critically, this limitation is about the **JS control-plane API being
  unreachable from a Worker** — it does **not** mean Worker-thread activity
  is invisible to tracing: V8/Node internals running *inside* a Worker still
  produce trace records (GC, compile, fs, etc. on that thread) into the
  **same, single, process-wide** trace file once a category is enabled from
  the main thread. This is the opposite of a per-realm/per-thread registry
  (contrast with `node:diagnostics_channel`, which *is* per-realm) — see §5.4.
- **No callback/promise variant anywhere in this module** — every function
  and method is fully synchronous; the actual disk I/O for writing trace
  records happens on a background thread/queue internally so it never blocks
  the thread that triggered an instrumented event (an implementation
  requirement, not a documented API guarantee, but necessary to avoid
  tracing itself perturbing the performance characteristics it's meant to
  observe).
- **Deprecations: none.** The whole module has been Experimental,
  unchanged in shape, since v10.0.0.
- **Security note.** Trace records can capture data some deployments
  consider sensitive: file paths (`node.fs*`), DNS/network endpoints
  (`node.dns.native`/`node.net.native`), HTTP metadata (`node.http`), and
  arbitrary `args` payloads a producer chooses to attach. Log files are
  written to disk in the current working directory by default (or wherever
  `--trace-event-file-pattern` points) with no built-in redaction — treat
  enabling tracing in a production deployment as a data-handling decision,
  not merely a performance-diagnostics toggle. This is worth calling out
  explicitly for RTS since the log file could inadvertently include
  request/response bodies or credentials if a future producer is careless
  about what it puts in `args`.
- **No Windows-vs-POSIX divergence in the documented JS-level API** — the
  category names, enable/disable semantics, and `getEnabledCategories()`
  behavior are platform-independent. The only platform-sensitive piece is
  the **default log file's location/writability** (cwd-relative path
  resolution differs only in the ordinary fs sense, not specific to this
  module) and, at the native level, the timestamp/PID/TID sourcing (`pid`
  and `tid` fields use OS-native process/thread identifiers, which differ in
  format between Windows and POSIX but are opaque numbers either way from
  the JS/file-format side).

## 5. RTS implementation notes

### 5.1 Native impl mapping

This module splits cleanly into two very different pieces:

1. **The public JS-visible control surface** (`Tracing`, `createTracing`,
   `getEnabledCategories`) — a small, cheap, pure in-memory **category
   reference-count registry**. No filesystem, network, or OS call is
   involved in this half at all. Backed by a plain Rust
   `HashMap<String, u32>` (category → active-reference-count) plus a
   separate `HashSet<String>` for the immutable CLI-supplied floor
   (populated once at process start from the RTS-equivalent of
   `--trace-event-categories`, see §5.8/§7), guarded by a single
   `std::sync::Mutex` (this registry is touched rarely — enable/disable
   calls and producer gate-checks — never in a per-allocation hot loop the
   way `HandleTable` is, so a plain mutex is adequate; no shard-based design
   needed here).
2. **The trace-event core: the actual file writer + the ~20 category
   *producers*** scattered across V8-equivalent (RTS engine) internals and
   every other Node module that instruments itself. This is the
   substantial, ongoing part of the work (§5.8) and depends on modules that
   do not exist yet for most categories.

**Not to be confused with the existing `rts-std::trace` namespace** (per
`.claude/rules/01-architecture.md`: "`trace/` — push/pop/capture/print frame
stack for Bun-style errors") — that is an unrelated feature (JS call-stack
capture for error messages), not Chrome-format event tracing. No code or
naming should be shared between the two; if `rts-std::trace` survives the
rts-std reduction (§2 of `architecture.md`) it stays entirely separate from
this module's native surface.

**Where the trace-event core lives:** because `v8`-category events must
originate **inside `rts-engine`'s own GC (mark+sweep) and Cranelift
compile/JIT code paths**, and `rts-engine` is the one crate that sits below
*every* other crate (`rts-node`, `rts-async`, `rts-primitives`, `rts-std`,
`rts-runtime`) per the acyclic crate graph, `rts-engine` cannot depend
upward on `rts-node` to report its own internal events. The category
registry, the record schema, and the file writer therefore belong in
**`rts-engine`** itself (a new small module, e.g. `rts_engine::trace`) —
analogous to how GC and the ABI/Registry already live there as
cross-cutting infra every higher crate consumes. Concretely:

- `rts-engine::trace::is_category_enabled(cat: &str) -> bool` and
  `rts-engine::trace::emit(cat, phase, name, args_json)` are plain Rust
  functions any code in `rts-engine` (GC, compiler) calls directly with zero
  cross-crate ceremony.
- `rts-node`'s `trace_events` extern functions (§5.2) are thin wrappers
  around `rts_engine::trace::{enable_categories, disable_categories,
  get_enabled_categories}` — a normal downward dependency (`rts-node`
  already depends on `rts-engine`).
- Any future producer living in `rts-node` (fs/net/dns/http/vm/console, once
  those modules exist) or in the hoisted `rts-async` crate (threadpool/
  promise-rejection producers, once that hoist lands) calls the same
  `rts_engine::trace::{is_category_enabled, emit}` pair — again a normal
  downward dependency, no new coupling.
- **File I/O** (`std::fs::File` opened in append mode, wrapped in a
  `std::io::BufWriter` behind the same mutex as the registry, or a
  dedicated writer thread fed by an `std::sync::mpsc` channel to keep
  producer call sites non-blocking) and **JSON encoding** use the
  `serde`/`serde_json` crates, already a workspace dependency (used today by
  `rts-std`'s JSON namespace) — `rts-engine` depending on `serde_json`
  directly is a normal third-party-crate dependency, not a forbidden
  dependency on the `rts-std` *crate*, so this does not violate the
  primordial/crate-partition doctrine.
- **Timestamp source:** a single canonical process-start
  `std::time::Instant`, stored once in `rts_engine::trace` (or reused from
  wherever `rts-node`'s own future `process.hrtime()`/`performance.now()`
  implementation anchors its epoch — the two **must** share one anchor
  point, not two independently-initialized `Instant`s, or `trace_events`
  timestamps would silently disagree with `process.hrtime()` by a few
  microseconds, violating the documented "same clock source" contract).
  Flagged explicitly as an implementation-order constraint in §5.8.

### 5.2 ABI surface

`Tracing` objects need **no `Handle`/HandleTable entry at all** — a
`Tracing` instance is fully represented by two plain fields
(`categories: string`, `enabled: boolean`) on an ordinary shape-based `.ts`
object; the *effect* of enable/disable lives entirely in the native registry
keyed by category **name**, not by any per-object identity. This mirrors the
`node:diagnostics_channel` spec's conclusion that `Channel` needs no native
handle — the engine's own shapes + data ICs already give the `.ts` object
fast property access.

Five `extern "C"` symbols, declared as `NodespaceMember`s in a new
`trace_events::SPEC` (module `"trace_events"`, `ns_prefix`
`"node_trace_events"`), following the existing `NodespaceSpec`/
`NodespaceMember` shape in `crates/rts-node/src/lib.rs` (mirrors the
`fs::SPEC`/`path::SPEC`/etc. pattern already there):

| Symbol | Args (`AbiType`) | Returns | Purpose |
|---|---|---|---|
| `__RTS_FN_NODE_TRACE_EVENTS_ENABLE_CATEGORIES` | `StrPtr` (comma-joined category list) | `Void` | Backs `tracing.enable()`. Splits the string, increments each category's reference count in the `rts-engine` registry (idempotent per-`Tracing`-instance — the `.ts` shim only calls this when its local `enabled` field transitions `false → true`, see §4). |
| `__RTS_FN_NODE_TRACE_EVENTS_DISABLE_CATEGORIES` | `StrPtr` (comma-joined category list) | `Void` | Backs `tracing.disable()`. Decrements each category's reference count (floored at the CLI-supplied set, which is never decremented below its own membership). Only called on the `enabled: true → false` transition. |
| `__RTS_FN_NODE_TRACE_EVENTS_GET_ENABLED_CATEGORIES` | none | `StrPtr` | Backs `getEnabledCategories()`. Returns the sorted, deduplicated, comma-joined union of (reference-count > 0) ∪ (CLI floor set). |
| `__RTS_FN_NODE_TRACE_EVENTS_IS_CATEGORY_ENABLED` | `StrPtr` (single category name) | `Bool` | **Producer-side fast-path check** — a single hashmap-membership lookup, called by every future instrumentation call site (in `rts-engine`, other `rts-node` modules, and eventually `rts-async`) *before* constructing an event's `args` payload, so a disabled category costs one lookup and nothing else (same zero-cost-when-unused discipline as `diagnostics_channel.hasSubscribers`). Not part of the public JS surface of this module — an internal producer-facing primitive, though nothing prevents another native module from calling it directly rather than round-tripping through TS. |
| `__RTS_FN_NODE_TRACE_EVENTS_EMIT` | `StrPtr` (category), `I32` (phase, encoded per the `ph` field in §3), `StrPtr` (event name), `StrPtr` (pre-serialized JSON `args`, or an empty string) | `Void` | The actual record-append primitive. Internally re-checks `is_category_enabled` (belt-and-suspenders — a producer that raced past the fast-path check while a `disable()` landed in between should still just no-op, never crash) and, if enabled, builds a `TraceEventRecord` (§3) with the shared timestamp/pid/tid and appends it to the writer queue. Not part of the public JS surface of this module either — every *other* module's native producer code calls this directly (Rust-to-Rust via `rts_engine::trace::emit`, not necessarily through this ABI symbol at all when the caller is already native code in the same process — the ABI symbol exists for the rare case a producer is itself written in `.ts` and needs a namespace-member call). |

Everything else in §2 (the `Tracing` class shape, `createTracing`,
`getEnabledCategories`'s comma-join/dedup/sort) is a **`.ts` shim** calling
only the first three externs — no marshalling beyond plain UTF-8 strings.

### 5.3 Async model

- Every function/method in this module's **public API** is fully
  **synchronous** — `createTracing`, `tracing.enable()`, `tracing.disable()`,
  `getEnabledCategories()` all complete immediately with no event-loop or
  tokio involvement.
- The **trace-record file writer** internally should not block the
  (arbitrary, possibly hot) thread that triggers an instrumented event.
  RTS's implementation should use a dedicated writer thread fed by an
  `std::sync::mpsc` channel (or an equivalent lock-free queue) so `emit()`
  from any thread (main, a rayon worker, a tokio worker) is a cheap
  enqueue, with the actual `File`/`BufWriter` I/O happening off that
  thread. This is an internal implementation detail with no JS-visible
  async surface — no `Promise`, no callback, nothing crosses the RTS
  Promise subsystem for this module.
- `node.promises.rejections` (a **category**, not a JS-callable function)
  is the one place this module conceptually touches the Promise subsystem:
  it needs a hook fired whenever RTS's own Promise machinery detects an
  unhandled rejection, so it can `emit()` a counter-style (`ph: "C"`) trace
  record. This requires the Promise subsystem (currently `rts-std`'s
  `promise` module) to expose such a hook once hoisted into `rts-async`
  (§5.7) — flagged, not implementable before that hoist lands.

### 5.4 Multithread / worker interaction

This module's threading story is the **opposite** of
`node:diagnostics_channel`'s (which is deliberately per-realm/thread-local):

- The category reference-count registry and the trace file writer are
  **process-wide, singleton, shared state** — one `rts_engine::trace`
  registry and one open log file (or rotation sequence) per RTS process,
  not one per thread/region. Every RTS thread (main, rayon `parallel`
  workers, tokio workers backing a future `rts-async`) that calls
  `rts_engine::trace::emit(...)` writes into the **same** file, exactly
  mirroring real Node's process-wide trace buffer.
- Per the RTS threading model (`docs/specs/rts-threading-model.md`), this
  places the registry + writer in the **shared-heap-adjacent, always-shared**
  category (like the GC's `HandleTable`, not like a `threadLocal` region) —
  it is not user-facing shared state subject to promotion-on-publication
  rules, it is engine-internal infra state guarded by its own lock, so the
  threading model's `threadLocal`/`shared`/`channel` surface does not apply
  to it directly (no user TS code ever holds a reference to the registry).
- **The public JS API is unreachable from inside a `worker_threads.Worker`**
  (per §4) — once `node:worker_threads` exists and maps a `Worker` onto an
  RTS thread/region (per the threading-model mapping in
  `docs/node-implementation/architecture.md` §8), the `node:trace_events`
  module resolver should either refuse to resolve the specifier inside a
  Worker context, or resolve it to a stub whose functions are documented
  no-ops — pick one and implement consistently (open question, §7,
  pending exact Node source behavior verification).
- Despite the API being unreachable from a Worker, **events produced by
  code running inside a Worker are NOT excluded** — a GC cycle, an `fs`
  sync call, etc. happening on a Worker's own OS thread still calls
  `rts_engine::trace::emit(...)` (same process-wide function every other
  thread calls) and lands in the same shared trace file, tagged with that
  thread's own `tid`.
- No new per-module thread-safety concern beyond "the registry's mutex is
  held for the shortest possible critical section" — enable/disable/
  get-enabled-categories are rare, low-contention calls; `emit()`'s hot path
  (`is_category_enabled`) should ideally be lock-free (e.g. an
  `arc_swap`'d or `RwLock`-read-guarded snapshot of the enabled set) so a
  disabled-category check from a hot GC/compile path never contends with
  an `enable()`/`disable()` call happening concurrently on another thread.

### 5.5 Buffer / TypedArray interop

Not applicable to this module's own logic. Trace record `args` payloads
(§3, `TraceEventRecord.args`) are always plain JSON-serializable values
(numbers, strings, booleans, nested plain objects/arrays) — there is no
byte-level ABI crossing defined by `trace_events` itself. If a future
producer wants to reference a `Buffer`/TypedArray-backed value in an event's
`args` (e.g. a `node.fs.async` record noting a read's byte count), it is
that *producer's* responsibility to extract a plain-number/string summary
(e.g. `.length`) before calling `emit()` — this module defines no mechanism
for embedding raw bytes in a trace record, matching how the upstream Chrome
Trace Event Format itself is JSON-only (no binary payloads).

### 5.6 Doctrine placement

`node:trace_events` is **non-primordial** — it has no native syntax, is
reached only through an explicit `node:` import, and the engine must never
hardcode its name. Resolution is 100% data-driven through rts-node's
existing tables, exactly like every other `node:` module: `ns_prefix_for
("node:trace_events")` → `"node_trace_events"` via a new
`trace_events::SPEC: NodespaceSpec` entry added to `NODE_SPECS` in
`crates/rts-node/src/lib.rs`, and `node_lookup("node_trace_events.<name>")`
for the five native members in §5.2. The bulk of the public-facing surface
(the `Tracing` class, `createTracing`, `getEnabledCategories`'s string
processing) is a **`.ts` shim** rts-node ships; the native member table is
intentionally tiny (5 members) because — exactly like
`diagnostics_channel` — the JS-visible feature itself needs almost no
native primitive; nearly all the real implementation work is the *producer*
call sites embedded inside other modules (§5.7/§5.8), not this module's own
table.

### 5.7 Shared-infra dependencies (FLAG)

- **The trace-event core itself (category registry + record schema + file
  writer) does not exist anywhere in RTS today — not in `rts-std`, not
  anywhere else.** This is not a "hoist an rts-std module" situation; it is
  new infra that must be built, and per §5.1 it is architecturally required
  to live in **`rts-engine`** (the one crate below every consumer, including
  `rts-engine`'s own GC/compiler) rather than in `rts-node` or a hoisted
  `rts-async`. Flagged prominently because it is the single largest
  prerequisite this module needs before *any* real category can be wired.
- **Shared tokio runtime / the `rts-async` hoist** (per
  `docs/node-implementation/architecture.md` §3.2/§7: `async_rt`,
  `event_loop`, promise settle, timers — currently living in `rts-std` and
  must move to a new low crate both `rts-std` and `rts-node` can depend on,
  since `rts-node` cannot depend on `rts-std`) — needed for:
  - `node.threadpoolwork.sync`/`node.threadpoolwork.async` (RTS's mapped
    equivalent of libuv's threadpool is the tokio `spawn_blocking` pool
    `rts-async` will expose).
  - `node.promises.rejections` (needs an unhandled-rejection hook on the
    Promise subsystem, §5.3).
  Neither category is implementable natively before this hoist lands;
  both can ship as **documented no-op categories** (enable/disable
  bookkeeping works, `getEnabledCategories()` reports them correctly, but
  no record is ever produced) in the interim, same "ships useful without
  the deferred part" pattern as `diagnostics_channel`'s `bindStore`.
- **`node:dns`/`node:net`/`node:http`/`node:vm` themselves** — needed as
  producer *hosts* for `node.dns.native`/`node.net.native`/`node.http`/
  `node.vm.script` respectively. Per core decision #1
  (`architecture.md` §2), these are independent `rts-node` modules RTS
  builds itself (not an rts-std hoist) — the dependency here is purely
  "that module must exist first", not "infra must move crates".
- **The rewritten `node:console`** (P0 tier per `architecture.md` §12,
  landing in `rts-node`, replacing the current `rts-shared`-hosted
  `.ts` console prelude) — needed as the producer host for `node.console`
  (`console.time()`/`console.count()` instrumentation). Until the
  rts-node console rewrite lands, this category is a documented no-op.
- **RTS's own process/module-loader bootstrap sequence** — needed to place
  well-defined instrumentation points for `node.bootstrap`/
  `node.environment`. This is new instrumentation of RTS's *own* startup
  code (`main.rs`/module resolution), not a hoist of anything existing.
- No fs/net/crypto/tls *primitive* beyond what's already flagged is needed
  — every producer module (`fs`, `net`, `dns`, `http`, `vm`) is itself an
  independent `rts-node` module per the crate-partition doctrine; this
  spec does not require `rts-node` to reach into `rts-std`'s equivalents.

### 5.8 Implementation phases

a. **Category registry skeleton, zero real event capture.** Add
   `rts_engine::trace` with the `HashMap<String, u32>` reference-count map +
   `HashSet<String>` CLI-floor set (initially always empty — no RTS CLI
   wiring yet), plus `enable_categories`/`disable_categories`/
   `get_enabled_categories`. Add the three corresponding externs (§5.2) and
   the `.ts` `Tracing` class + `createTracing`/`getEnabledCategories`. This
   alone makes the full public API surface (§2) observably correct —
   union/ref-count semantics, coercion errors, idempotent enable/disable —
   testable with zero producers wired.
b. **`is_category_enabled` + `emit` + the JSON record writer.** Add the
   `TraceEventRecord` struct (`serde::Serialize`), the two remaining
   externs, and a background-thread writer (`mpsc` channel →
   `BufWriter<File>`) targeting the default `node_trace.${rotation}.log`
   naming. Anchor the shared canonical `Instant` (§5.1) — coordinate with
   whichever RTS component ends up owning `process.hrtime()`'s epoch so
   the two never diverge.
c. **First real producer: `v8`-equivalent GC events from `rts-engine`'s own
   collector.** Cheapest possible end-to-end proof (same crate, zero new
   cross-crate wiring) — instrument `mark_stack_roots`/`sweep_all_shards`
   cycle boundaries as `ph: "B"`/`"E"` pairs. Validates the whole pipeline:
   category gate → record → file → parseable by a `chrome://tracing`-
   compatible viewer.
d. **`node`/`node.bootstrap`/`node.environment` milestones** from RTS's own
   process/module-loader startup sequence.
e. **`node.console`** once the rewritten `rts-node` console lands
   (`console.time`/`console.count` instrumentation).
f. **`node.fs.sync`/`node.fs_dir.sync`** once `node:fs`'s sync surface
   exists (P0 tier, likely available earliest among the fs-adjacent
   categories).
g. **`node.threadpoolwork.sync`/`.async`, `node.fs.async`/
   `node.fs_dir.async`, `node.promises.rejections`** — all gated on the
   `rts-async` hoist (§5.7) landing; implement together once it does, since
   they share the same underlying "was this scheduled on the shared
   blocking pool" instrumentation point.
h. **`node.dns.native`/`node.net.native`/`node.http`/`node.vm.script`/
   `node.module_timer`** — opportunistic, one per owning module, as each
   of `node:dns`/`node:net`/`node:http`/`node:vm`/the CJS module loader is
   itself implemented. Not a blocker for this module's own completeness,
   tracked as N separate per-module follow-ups (same pattern as
   `diagnostics_channel`'s built-in-channel backfill, §5.8f there).
i. **RTS CLI flags** (`--trace-event-categories`, `--trace-event-file-pattern`,
   and an RTS equivalent of `--trace-events-enabled`) wired into `rts-cli`,
   populating the `rts_engine::trace` CLI-floor set at process startup
   before user code runs. Cross-cutting CLI work, not blocking any of the
   above phases (open question on exact flag names/shape, §7).

## 6. Test plan

- **Basic enable/getEnabledCategories roundtrip.** `createTracing({categories:
  ["node.perf"]}).enable()`; assert `getEnabledCategories()` contains
  `"node.perf"`.
- **Union across two overlapping `Tracing` objects.** `t1 = createTracing({
  categories: ["node", "v8"] })`, `t2 = createTracing({ categories:
  ["node.perf", "node"] })`; `t1.enable(); t2.enable()`; assert
  `getEnabledCategories()` is exactly `{"node", "node.perf", "v8"}` (order-
  independent set comparison). `t2.disable()`; assert the result is now
  exactly `{"node", "v8"}` — `"node"` survives because `t1` still holds it.
- **`disable()` idempotency / double-enable guard.** Call `t1.enable()`
  twice in a row, then `t1.disable()` once; assert every category `t1`
  covered is now fully gone from `getEnabledCategories()` (proves the
  reference count was not double-incremented).
- **`tracing.enabled` reflects only this object's own state**, independent
  of whether its categories are also held enabled by another `Tracing`
  object — `t2.disable()` sets `t2.enabled === false` even though `"node"`
  itself is still globally enabled via `t1`.
- **Coercion / error path.** `createTracing({ categories: [42, "ok"] })`
  succeeds (`42` coerces to `"42"`); `createTracing({ categories: [{}] })`
  (or another non-coercible value) throws.
- **Empty baseline.** A fresh process with no CLI tracing flags and no
  `createTracing().enable()` call anywhere: assert
  `getEnabledCategories() === ""`.
- **Fast-path no-op when disabled.** With a category never enabled, call
  a (once-implemented) producer path guarded by
  `is_category_enabled`/`emit`; assert a side-effect counter proving the
  expensive `args` object was never constructed (mirrors the
  `hasSubscribers` fast-path test pattern from the `diagnostics_channel`
  spec).
- **End-to-end record shape (once phase c/d lands).** Enable `v8` (or
  `node.bootstrap`), trigger a real GC cycle / process-start milestone,
  read back the emitted `node_trace.*.log`, `JSON.parse` it, and assert
  each record matches the `TraceEventRecord` schema (§3): required
  `name`/`cat`/`ph`/`ts`/`pid`/`tid` present, types correct, `ts`
  monotonically non-decreasing within one thread's records.
- **CLI-floor category cannot be disabled from JS** (once phase i lands).
  Start a process-equivalent test harness with an RTS CLI tracing flag
  pre-set to a category; assert no `Tracing.disable()` call removes it
  from `getEnabledCategories()`.
- **Multithread visibility (once a `rayon`/tokio-backed producer exists).**
  Enable a category from the main thread; trigger a producer event on a
  `parallel` worker thread or a tokio worker; assert the resulting record
  lands in the **same single** trace file as main-thread records (proves
  process-wide, not per-thread, registry — the key behavioral difference
  from `node:diagnostics_channel`'s per-realm model).
- **Worker-thread unavailability (guarded until `node:worker_threads`
  lands).** Attempt to `import "node:trace_events"` (or call one of its
  functions) from inside a Worker; assert whichever documented behavior RTS
  chose (throw, or inert no-op — see §7) occurs consistently.
- **File rotation (once a concrete rotation policy is implemented).**
  Force enough trace volume to cross RTS's chosen rotation threshold;
  assert the filename's `${rotation}` component increments and both files
  are independently valid JSON.

## 7. Open questions / deferrals

- **Exact semantics of `node.threadpoolwork.sync` vs `node.threadpoolwork.async`.**
  The public docs describe them only as "synchronous operations" vs
  "asynchronous operations" on the threadpool, which is ambiguous (both
  categories instrument work that is fundamentally asynchronous from the
  caller's perspective in real Node/libuv — the split more likely
  distinguishes the submission/queueing phase from the worker-thread
  execution phase, not "sync API" vs "async API"). Verify against Node/V8
  source before wiring phase g; functionally both map onto RTS's
  `rts-async` blocking-pool submit/execute boundary either way.
- **Exact file-rotation trigger.** Not documented at the public-API level
  (event count? byte size? one rotation per V8 internal trace-buffer
  flush?). RTS's own policy need not be byte-identical to V8's — only the
  externally-observable contract (`${rotation}` increments monotonically,
  each file is independently valid) must hold; verify Node/V8 source if
  exact parity with a specific numeric threshold is ever required.
- **Exact behavior when imported/used inside a `Worker`.** "Not available"
  is stated flatly with no operational detail (throw at import time? throw
  per-call? silently inert?). Needs verification against Node source once
  `node:worker_threads` exists in RTS and this becomes testable; pick one
  behavior and document it as the RTS parity choice rather than leaving it
  ambiguous.
- **`getEnabledCategories()`'s exact empty-set return value.** Documented
  prose doesn't pin down `""` vs some other falsy value for "nothing
  enabled" across all Node versions — target `""` for RTS (§2.2) unless a
  concrete counter-example from Node source is found.
- **RTS CLI flag surface** for the equivalents of `--trace-event-categories`,
  `--trace-event-file-pattern`, and `--trace-events-enabled` needs an
  explicit owner decision in `rts-cli` (flag names, whether RTS mirrors
  Node's exact flag spelling for muscle-memory parity or picks RTS-native
  names) — out of this module's own native-surface scope, tracked as a
  cross-cutting CLI task (§5.8i).
- **Whether RTS should target byte-for-byte Chrome Trace Event Format, or a
  simpler RTS-native diagnostic format with a documented divergence.**
  Chrome/Perfetto-viewer compatibility is a nice-to-have parity feature for
  developer experience, not a JS-semantics correctness requirement (no user
  TS/JS code can observe the file's *format*, only that `getEnabledCategories`/
  `enable`/`disable` behave correctly) — recommend targeting the documented
  JSON Trace Event Format (§3) since it costs little extra and preserves
  the "open in chrome://tracing" workflow real Node users expect, but
  flagging as an owner-confirmable choice rather than an assumed
  requirement.
- **Interaction with `node:perf_hooks`** (P1 tier, not yet specced in this
  docs folder) for the `node.perf`/`node.perf.usertiming`/
  `node.perf.timerify` categories — those producers naturally live inside
  whatever native `PerformanceObserver`/`performance.mark`/`timerify`
  implementation `node:perf_hooks` ends up with; deferred until that
  module's own spec exists.
- **`node.module_timer`'s relationship to ESM vs CJS loading.** The category
  name and its one-line doc ("CJS Module loading") suggest it is CJS-
  `require()`-specific; whether an RTS ESM `import` equivalent should also
  produce comparable timing records (under the same category or a new one)
  is unresolved — defer to whoever implements RTS's module loader
  instrumentation.

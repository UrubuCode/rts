## 1. Purpose

In real Node.js, `node:v8` is a window into the **V8 JavaScript engine build embedded in Node**: heap/memory introspection (`getHeapStatistics`, `getHeapSpaceStatistics`, heap snapshots), V8's structured-clone wire serializer (`serialize`/`deserialize`, `Serializer`/`Deserializer`), V8 command-line-flag injection (`setFlagsFromString`), code-coverage extraction (`takeCoverage`/`stopCoverage`), GC and CPU profiling handles, Promise-lifecycle hooks, and the V8 startup-snapshot builder API. Every function name and returned field in Node's own docs mirrors a V8 C++ concept (`v8::HeapStatistics`, `v8::ValueSerializer`, `v8::V8::SetFlagsFromString`, cppgc, `SnapshotCreator`) — because in Node, that is literally what backs it.

**RTS has its own compiler and runtime engine and never embeds, emulates, or links V8** — this is a binding project rule, not a per-module choice (`docs/node-implementation/architecture.md` §11, core decision 3). RTS compiles TS/JS to native code via Cranelift and manages memory with its own mark+sweep collector over a `HandleTable`/shape model (`rts-engine`). `node:v8`'s **API surface** — every function signature, every class, every returned field shape — is reproduced faithfully for parity, for **all callers**, but every single member is backed by an **RTS-engine equivalent**, never a V8 instance, a V8 heap, or a V8 flag interpreter:

- Heap/memory introspection maps onto RTS's own mark+sweep collector and `HandleTable` statistics.
- The structured-clone serializer maps onto **RTS's own structured-serialize primitive** — RTS's own wire format, sharing the same value-traversal design as the ambient `structuredClone()` global, not V8's `ValueSerializer` byte format.
- Flag injection maps onto a small, curated set of RTS engine tunables, with a documented no-op fallback for everything else.
- Heap snapshots are written in **RTS's own** JSON schema, not V8's DevTools `.heapsnapshot` format.
- GC/CPU profiling, coverage, and Promise hooks map onto RTS-engine hooks that already exist or are flagged as new compiler/runtime work — never a stub that quietly pretends to be V8.

This is the same posture the sibling `node:vm`/`node:inspector` specs take for their own V8-coupled surface (`architecture.md` §11). §5 below states, member by member, which RTS mechanism backs each one, and marks plainly which figures are real measured RTS quantities versus documented placeholders where RTS genuinely has no analogous concept (e.g. V8 build-flag internals like `does_zap_garbage`) — never a fabricated number dressed up to look like a real V8 statistic.

#### Class: `v8.Serializer`

Base class for the structured-clone wire-format writer. Node code rarely instantiates `Serializer` directly (it uses `DefaultSerializer` or the `serialize()` convenience function) except to subclass it and override the `_write*`/`_get*` protected hooks for host-object handling.

- **`new v8.Serializer()`** — constructor, no arguments.
- **`serializer.writeHeader()`** — params: none; returns `void`. Writes the format-version header; must run before the first `writeValue()` (or before any custom `_write*` call) when subclassing without `writeValue`'s implicit header write.
- **`serializer.writeValue(value)`** — params: `value: any`; returns `void`; throws (or the value returned by an overridden `_getDataCloneError`) if `value` cannot be serialized (a function, a `WeakMap`, a native/host object with no `_writeHostObject` override, a `Symbol`).
- **`serializer.releaseBuffer()`** — params: none; returns `Buffer`. Returns the accumulated byte buffer; **the serializer is unusable after this call**.
- **`serializer.transferArrayBuffer(id, arrayBuffer)`** — params: `id: integer` (32-bit unsigned), `arrayBuffer: ArrayBuffer`; returns `void`. Marks the `ArrayBuffer` as transferred out-of-band; the receiving `Deserializer` must call `transferArrayBuffer(id, arrayBuffer)` with the same `id` before `readValue()`.
- **`serializer.writeUint32(value)`** — params: `value: integer`; returns `void`. Raw 32-bit unsigned write, for `_writeHostObject()`.
- **`serializer.writeUint64(hi, lo)`** — params: `hi: integer`, `lo: integer`; returns `void`.
- **`serializer.writeDouble(value)`** — params: `value: number`; returns `void`. Raw IEEE-754 double write.
- **`serializer.writeRawBytes(buffer)`** — params: `buffer: Buffer | TypedArray | DataView`; returns `void`. Appends raw bytes verbatim (paired with `deserializer.readRawBytes(length)`).
- **`serializer._writeHostObject(object)`** *(protected override point)* — params: `object: Object`; returns implementation-defined (must ultimately call `writeUint32`/`writeRawBytes`/etc.); default throws a data-clone error.
- **`serializer._getDataCloneError(message)`** *(protected override point)* — params: `message: string`; returns `Error` (or subclass) to throw for unserializable values; default constructs a plain `Error`.
- **`serializer._getSharedArrayBufferId(sharedArrayBuffer)`** *(protected override point)* — params: `sharedArrayBuffer: SharedArrayBuffer`; returns `integer` (unsigned 32-bit) identifying it; default throws.
- **`serializer._setTreatArrayBufferViewsAsHostObjects(flag)`** *(protected)* — params: `flag: boolean` (default `false`); returns `void`. When `true`, `TypedArray`/`DataView` route through `_writeHostObject` instead of the built-in typed-array encoding.

#### Class: `v8.Deserializer`

- **`new v8.Deserializer(buffer)`** — constructor; params: `buffer: Buffer | TypedArray | DataView` (must be produced by a matching `Serializer.releaseBuffer()`).
- **`deserializer.readHeader()`** — params: none; returns `void`; throws if the format-version header is missing/unrecognized/unsupported.
- **`deserializer.readValue()`** — params: none; returns `any` — the next deserialized value.
- **`deserializer.transferArrayBuffer(id, arrayBuffer)`** — params: `id: integer`, `arrayBuffer: ArrayBuffer | SharedArrayBuffer`; returns `void`.
- **`deserializer.getWireFormatVersion()`** — params: none; returns `integer`; only meaningful after `readHeader()`.
- **`deserializer.readUint32()`** — params: none; returns `integer`.
- **`deserializer.readUint64()`** — params: none; returns `[integer, integer]` (`[hi, lo]`).
- **`deserializer.readDouble()`** — params: none; returns `number`.
- **`deserializer.readRawBytes(length)`** — params: `length: integer`; returns `Buffer`; must exactly match the corresponding `writeRawBytes()` byte count.
- **`deserializer._readHostObject()`** *(protected override point)* — params: none; returns implementation-defined value; default throws.

#### Class: `v8.DefaultSerializer`

Extends `v8.Serializer`. Overrides the host-object hooks to encode `TypedArray`/`Buffer`/`DataView` by storing only the portion of the referenced `ArrayBuffer` they view — the concrete class `v8.serialize()` uses internally.

#### Class: `v8.DefaultDeserializer`

Extends `v8.Deserializer`. The matching reader for `DefaultSerializer`'s format; used internally by `v8.deserialize()`.

#### Class: `v8.GCProfiler`

- **`new v8.GCProfiler()`** — constructor, no arguments. Supports `using` (`using profiler = new v8.GCProfiler()` auto-disposes at scope exit).
- **`profiler.start()`** — params: none; returns `void`. Begins collecting GC-cycle timing + before/after heap statistics.
- **`profiler.stop()`** — params: none; returns `GCProfilerResult` (§3). Each recorded entry pairs a GC cycle's `gcType`, `cost` (duration), and full heap/heap-space statistics immediately before and after that cycle.
- **`profiler[Symbol.dispose]()`** — params: none; returns `void`. Stops collection (if running) and **discards** the profile (does not return it).

#### Class: `SyncCPUProfileHandle`

Returned by `v8.startCpuProfile()`. Supports `using`.

- **`handle.stop()`** — params: none; returns `string` — stops collecting and returns the profile data (`.cpuprofile`-shaped JSON string) synchronously.
- **`handle[Symbol.dispose]()`** — params: none; returns `void` — stops collecting and **discards** the profile.

#### Class: `CPUProfileHandle`

Async counterpart of `SyncCPUProfileHandle`. **(verify — no public Node 25 function is documented as returning this class; see §7.)**

- **`handle.stop()`** — params: none; returns `Promise<string>`.
- **`handle[Symbol.asyncDispose]()`** — params: none; returns `Promise<void>`; supports `await using`.

#### Class: `HeapProfileHandle`

Async heap-profile handle. **(verify — same caveat; its starter function `v8.startHeapProfile()` is tagged v26.1.0/Experimental on Node's main-branch docs, i.e. post-25 — see §7.)**

#### `v8.cachedDataVersionTag()`

- **Params:** none.
- **Returns:** `integer` — in real Node, a tag derived from the V8 version, flags, and CPU features, used to check whether a `vm.Script`'s bytecode cache is compatible with the current process before consuming it.
- **Throws:** never.

#### `v8.getHeapStatistics()`

- **Params:** none.
- **Returns:** `HeapStatistics` (§3) — 15 fields covering total/used/available heap size, executable size, physical size, malloc'd memory, native-context counts, and `external_memory`.
- **Throws:** never.

#### `v8.getHeapSpaceStatistics()`

- **Params:** none.
- **Returns:** `HeapSpaceStatistics[]` (§3) — one entry per heap "space"; RTS's synthesized space list is documented in §5.1.
- **Throws:** never.

#### `v8.getHeapCodeStatistics()`

- **Params:** none.
- **Returns:** `HeapCodeStatistics` (§3) — 4 fields describing memory used by compiled-code metadata and bytecode.
- **Throws:** never.

#### `v8.getCppHeapStatistics([detailLevel])`

- **Params:** `detailLevel?: 'brief' | 'detailed'` (default `'detailed'`).
- **Returns:** `CppHeapStatistics` (§3); `space_statistics`/`type_names` populated only when `detailLevel === 'detailed'`.
- **Throws:** `TypeError` for an invalid `detailLevel`.

#### `v8.setFlagsFromString(flags)`

- **Params:** `flags: string` — one or more V8 command-line flags in real Node, e.g. `'--trace-gc'`, `'--max-old-space-size=100'`.
- **Returns:** `void`.
- **Throws:** never documented to throw for a syntactically valid flag string; Node's own docs warn behavior is unpredictable for flags not meant to be changed post-startup ("may result in unpredictable behavior... or it may simply do nothing").
- **Note:** most-used in real Node for `--expose-gc` or trace/tuning flags.

#### `v8.setHeapSnapshotNearHeapLimit(limit)`

- **Params:** `limit: integer` — positive integer; max auto-written snapshots.
- **Returns:** `void`.
- **Throws:** `ERR_INVALID_ARG_TYPE`/`ERR_OUT_OF_RANGE` for a non-positive-integer `limit`.
- Configures automatic snapshot writing (equivalent to `writeHeapSnapshot()`) when the heap approaches `heap_size_limit`, up to `limit` times — a near-OOM diagnostic aid.

#### `v8.getHeapSnapshot([options])`

- **Params:** `options?: { exposeInternals?: boolean (default false); exposeNumericValues?: boolean (default false) }`.
- **Returns:** `stream.Readable` — a Readable emitting the heap snapshot as JSON.
- **Throws:** never (stream-level errors surface as `'error'` events, not a synchronous throw).

#### `v8.writeHeapSnapshot([filename[, options]])`

- **Params:** `filename?: string` (auto-generated as `Heap-<yyyymmdd>-<hhmmss>-<pid>-<threadid>.heapsnapshot` if omitted); `options?: { exposeInternals?: boolean; exposeNumericValues?: boolean }`.
- **Returns:** `string` — the path actually written.
- **Throws:** `Error`/`SystemError` on filesystem write failure.

#### `v8.serialize(value)`

- **Params:** `value: any`.
- **Returns:** `Buffer` — the structured-clone-compatible serialized form; in Node, internally constructs a `DefaultSerializer`, calls `writeHeader()` + `writeValue(value)`, returns `releaseBuffer()`. RTS's implementation reuses its own structured-serialize primitive directly (§5.1).
- **Throws:** `ERR_BUFFER_TOO_LARGE` if the result would exceed `buffer.constants.MAX_LENGTH`; a data-clone error for genuinely unclonable values (functions, most host objects with no clone support).

#### `v8.deserialize(buffer)`

- **Params:** `buffer: Buffer | TypedArray | DataView` — must be a value previously produced by `serialize()` or an equivalent `Serializer`.
- **Returns:** `any` — the reconstructed value.
- **Throws:** `Error` if the header is invalid/unsupported, or the byte stream is truncated/corrupt mid-value.

#### `v8.takeCoverage()`

- **Params:** none. **Returns:** `void`.
- In real Node, writes coverage collected so far (only active when the process was started with `NODE_V8_COVERAGE=<dir>`) to disk as a JSON file per Node's `v8-coverage` format. Can be called multiple times; each call resets internal counters.

#### `v8.stopCoverage()`

- **Params:** none. **Returns:** `void`.
- Stops coverage collection. Does **not** itself write a file — call `takeCoverage()` first to persist collected data.

#### `v8.isStringOneByteRepresentation(content)`

- **Params:** `content: string`.
- **Returns:** `boolean` — in real Node, whether V8 is internally storing this exact string using a one-byte-per-character representation rather than two-byte UTF-16 (a V8-internal storage-optimization fact). RTS's implementation is a documented approximation (§5.1).
- **Throws:** `TypeError` if `content` is not a string.

#### `v8.queryObjects(ctor[, options])`

- **Params:** `ctor: Function`; `options?: { format?: 'count' | 'summary' }` (default `'count'`).
- **Returns:** `number` (default) — count of matching live objects; or `string[]` (`'summary'`) — one short representation per matching object.
- **Throws:** never documented; degrades to `0`/`[]` if no matches. Triggers a full GC first (so unreferenced-but-not-yet-collected objects are excluded) and only counts objects in the **current execution context** (realm).
- Example (from Node docs): a class `B extends A`; instances of `B` are also matched by `queryObjects(A)`.

#### `v8.startCpuProfile()`

- **Params:** none. **Returns:** `SyncCPUProfileHandle`.
- Starts CPU-profile collection immediately; `.stop()` synchronously ends collection and returns the profile JSON string. Supports `using`.

### 2.3 Namespace objects

#### `v8.promiseHooks`

Tracks the Promise lifecycle. Every callback **must be a non-async function** (an async callback would itself create Promises, recursively re-entering the hook).

- **`v8.promiseHooks.onInit(init)`** — params: `init: (promise, parent) => void`; returns `() => void` (unregister). Fires when a new Promise is created; `parent` is the promise being chained from, if any.
- **`v8.promiseHooks.onSettled(settled)`** — params: `settled: (promise) => void`; returns `() => void`. Fires once a Promise settles.
- **`v8.promiseHooks.onBefore(before)`** — params: `before: (promise) => void`; returns `() => void`. Fires immediately before a Promise's reaction runs.
- **`v8.promiseHooks.onAfter(after)`** — params: `after: (promise) => void`; returns `() => void`. Fires immediately after a Promise's reaction finishes (or an `await` resumes).
- **`v8.promiseHooks.createHook(callbacks)`** — params: `callbacks: { init?, before?, after?, settled? }`; returns `() => void` (disables all four). Batch-registration convenience.

#### `v8.startupSnapshot`

Only meaningful in real Node when the process runs under V8's `--build-snapshot` mode.

- **`v8.startupSnapshot.addSerializeCallback(callback[, data])`** — params: `callback: (data) => void`, `data?: any`; returns `void`.
- **`v8.startupSnapshot.addDeserializeCallback(callback[, data])`** — same signature; runs after deserialization.
- **`v8.startupSnapshot.setDeserializeMainFunction(callback[, data])`** — same signature; sets the post-deserialize entry point; **may only be called once** per snapshot build.
- **`v8.startupSnapshot.isBuildingSnapshot()`** — params: none; returns `boolean`.

## 4. Node semantics & edge cases

- **This module's original purpose is V8 introspection; RTS answers every question with an RTS-native fact instead of a V8 one.** In real Node, every field/return value is either a faithful RTS-internal analog of the V8 concept it names (e.g. live handle bytes → `used_heap_size`) or, where V8's concept has no RTS analog at all (a V8-build-flag toggle like `does_zap_garbage`, or a per-`Context` count RTS has no multi-realm model for yet), a documented placeholder value. §5.1 marks each field's provenance explicitly and this is never hidden once implemented — no field is silently fabricated to look like a plausible V8 number.
- **`serialize`/`deserialize`'s wire format is not cross-version-guaranteed even in real Node** — Node's docs state the format may change across Node versions and must not be relied on for long-term storage or cross-version `postMessage`. This matters for RTS: RTS's own wire format does **not** need to be byte-compatible with V8's `ValueSerializer` output, since Node itself makes no such guarantee across its own versions — only internally self-consistent (RTS `serialize` output round-trips through RTS `deserialize`). Byte-level compatibility with real Node's format is explicitly out of scope (§7).
- **`getHeapSnapshot()` returns a stream, `writeHeapSnapshot()` writes to disk and returns the path** — same underlying snapshot content, different result shapes; both accept the same `{exposeInternals, exposeNumericValues}` options.
- **The heap-snapshot JSON body schema is not itself part of Node's stable documented API contract** — Node's docs specify the function signatures and options but not a versioned schema for the JSON body (in real Node, that body is whatever the linked V8 build happens to produce, consumed today mainly by Chrome DevTools' Memory tab). RTS is therefore free to emit its **own** JSON schema for the snapshot body (§5.1) rather than reproducing V8's DevTools `nodes`/`edges`/`strings` flat-array format; DevTools-loadability is an optional, out-of-scope stretch goal, not a parity requirement (§7).
- **`ERR_BUFFER_TOO_LARGE`** is the one documented `serialize()` error code, thrown when the serialized result would exceed `buffer.constants.MAX_LENGTH`.
- **`Serializer`/`Deserializer` are stateful, single-use-ish objects**: `releaseBuffer()` invalidates further writes; a `Deserializer` must have `readHeader()` called before `readValue()`/`getWireFormatVersion()`; `transferArrayBuffer` ids must match between the serializing and deserializing sides for any `ArrayBuffer` explicitly transferred (as opposed to deep-copied).
- **`setFlagsFromString` has explicitly unpredictable documented behavior even in real Node.** Most flags are meant to be set at startup only; calling this after boot "may simply do nothing" for many of them. This gives RTS legitimate latitude to implement only a curated subset of flags with real RTS-side effects and document-and-no-op the rest — matching real-Node behavior, not a parity shortfall (§5.1).
- **`queryObjects()` forces a full GC and only searches the current execution context (realm)** — objects created in a different `vm.Context`/worker realm are excluded even if reachable; RTS must replicate this constraint against its own notion of "region" (§5.4, §7).
- **`isStringOneByteRepresentation` is a V8-internal-storage fact, not a Unicode-range predicate** — a string that is entirely ASCII/Latin-1-content is not guaranteed to return `true` in real V8 (V8 may keep it as UTF-16 depending on construction history). RTS, which always stores strings as UTF-8, can only offer a principled **approximation** and must document it as such (§5.1) rather than claim to measure an internal representation RTS doesn't have.
- **Explicit Resource Management (`using`/`await using`) dependency.** `GCProfiler`, `SyncCPUProfileHandle`, `CPUProfileHandle`, and `HeapProfileHandle` all support `using`/`await using` (`[Symbol.dispose]`/`[Symbol.asyncDispose]`) — a TC39/TS 5.2+ language feature RTS's parser/HIR must support **independently of this module** before these classes are spec-compliant; a cross-cutting language-support prerequisite, not something `rts-node` can implement in isolation (§7).
- **No deprecations exist in this module** as of Node 25.
- **Coverage collection (`takeCoverage`/`stopCoverage`) requires `NODE_V8_COVERAGE=<dir>` to have been set before process start** — calling `takeCoverage()` without it set is a documented no-op.
- **Security note.** Heap snapshots and `queryObjects({format:'summary'})` output can capture the **entire contents of every live string/object in the process**, including secrets never intended to reach disk. RTS applies no additional redaction beyond what Node itself does (none) — worth calling out explicitly to implementers and in RTS's own user-facing docs.
- **No backpressure concerns beyond the `getHeapSnapshot()` stream itself** — everything else is a single bounded synchronous call.

## 5. RTS implementation notes

### 5.1 Native impl mapping

**Binding constraint (`architecture.md` §11): RTS never embeds, emulates, or links V8. Every member below is backed by an RTS-engine mechanism, not a V8 stand-in.** `rts-node` is a fully independent crate depending only on `rts-engine` (+ `rts-async` once hoisted). This module is unusual among `node:*` specs in that **most of it needs no hoist at all** — the RTS mechanisms it maps onto already live in `rts-engine` (`heap::{handles, poly, shapes, class_registry}`, `collector::{mod, scan, thread_registry, global_roots}`), which `rts-node` already depends on directly. Contrast with `node:dns`/`node:net`, which need the tokio/async stack that lives in `rts-std`.

- **Heap statistics group (`getHeapStatistics`/`getHeapSpaceStatistics`/`getHeapCodeStatistics`/`getCppHeapStatistics`).** RTS has no V8-style generational/paged heap with named spaces — it has a shard-based `HandleTable` (32 shards) plus native-stack-allocated/Cranelift-JIT-or-AOT-compiled function memory. Field-by-field provenance, mapped onto that real RTS structure:
  - `used_heap_size`/`total_heap_size` — **real**: sum of live handle payload byte sizes across all 32 `HandleTable` shards (`live_handle_count()` × per-`Entry`-variant size where known) plus the shape/slot arrays backing live objects (`rts-engine::heap::shapes`). Reflects RTS's actual managed-memory footprint.
  - `total_heap_size_executable`/`total_physical_size` — **approximated**: derived from the JIT/AOT module's compiled-code region size (`cranelift_jit::JITModule`'s allocated executable pages under `rts run`; the linked binary's `.text` size under `rts compile`) — a slower-changing figure than V8's live-growing one, marked as approximated.
  - `heap_size_limit` — RTS's own configurable soft heap-limit knob; **real once the knob exists** (ties directly into `setHeapSnapshotNearHeapLimit` below; needs adding if it doesn't exist yet).
  - `malloced_memory`/`peak_malloced_memory` — from the global Rust allocator; real if a stats-capable allocator is in use, otherwise approximated via a tracking-allocator wrapper (`std::alloc::GlobalAlloc` shim) — flagged as new native work, not reuse of an existing counter.
  - `does_zap_garbage` — **documented placeholder, fixed `0`**: a V8 build-flag concept (whether freed memory is poison-filled in debug builds) with no RTS analog; RTS's collector does not zap freed slots today.
  - `number_of_native_contexts`/`number_of_detached_contexts` — **documented placeholder, `1`/`0`**: RTS has no multi-realm `vm.Context` model yet (single implicit realm), revisited if/when one is added.
  - `total_global_handles_size`/`used_global_handles_size` — **real**: `HandleTable`'s total slot-array capacity vs `live_handle_count()` across all shards, scaled by per-variant size — a broader concept than V8's narrower "persistent GC roots", documented as an intentional broad-but-honest analog.
  - `external_memory` — **real**: sum of byte sizes for `Entry` variants representing externally-backed memory outside the primary managed heap (`Buffer`/`ArrayBuffer` raw allocations, native socket/file handles).
  - `total_allocated_bytes` — **real once added**: a monotonic cumulative-allocation counter, alongside the tracking-allocator work above.
  - **Heap spaces (`getHeapSpaceStatistics`)** — RTS synthesizes its own small, honestly-named space list: `rts_handles` (aggregated `HandleTable` shards), `rts_code` (JIT/AOT compiled-code region), `rts_external` (raw `Buffer`/`ArrayBuffer` byte storage) — fewer, differently-named spaces than V8's `new_space`/`old_space`/`code_space`/`map_space`/`large_object_space`/`read_only_space`/`new_large_object_space`. Shape-compatible (an array of `{space_name, space_size, space_used_size, space_available_size, physical_space_size}`), not name-compatible; documented plainly.
  - **`getHeapCodeStatistics`** — `code_and_metadata_size`/`bytecode_and_metadata_size` map onto Cranelift-compiled-function memory size; `external_script_source_size` maps onto retained original TS/JS source text RTS keeps for error messages/`Function.prototype.toString()`; `cpu_profiler_metadata_size` maps onto whatever bookkeeping `v8.startCpuProfile()`'s implementation retains while active (`0` when idle).
  - **`getCppHeapStatistics`** — the RTS analog of V8's separate cppgc heap (C++-wrapped native objects) is the **non-GC-scanned Rust-native handle payloads** — sockets, file handles, process children, native crypto contexts, etc. (the "rich object as opaque Handle" pattern used throughout `rts-node`'s sibling modules). `space_statistics`/`type_names` (detailed mode) enumerate these by category.
- **`serialize`/`deserialize`/`Serializer`/`Deserializer`/`DefaultSerializer`/`DefaultDeserializer` → RTS's own structured-serialize primitive, reusing the `structuredClone()` deep-walk design.** RTS does **not** reproduce V8's `ValueSerializer` byte tags (per §4, not required). Instead:
  - RTS defines **one canonical structured-serialize primitive** — a tag-prefixed recursive encode/decode over an arbitrary live value: `undefined`, `null`, `boolean`, `int32`/`float64` number, `bigint`, UTF-8 `string`, `Array`, plain `Object` (shape-driven key/value pairs), `ArrayBuffer`/`TypedArray`/`DataView`, `Date`, `RegExp`, `Error`-family instances, with `Map`/`Set` support gated on the class-identity question below. This walk needs nothing beyond what `rts-node` already has reachable through `rts-engine`: reading a `PolyValue`'s tag, and for object/array tags walking the `Shape`'s slot layout (`rts-engine::heap::poly`/`shapes`).
  - **This is deliberately the same conceptual traversal the ambient `structuredClone()` global already needs** — today `structuredClone()`'s deep-clone walk is implemented as `.ts` (`rts-shared/src/stdlib/structured_clone.ts`), walking values via ordinary property access rather than a dedicated native wire-format encoder, because in-memory deep-clone never needed a byte format before. `node:v8` is what actually *introduces the need* for a byte-serialized wire format. The correct target architecture is **one native structured-serialize primitive living in `rts-engine`** (the lowest crate both `rts-shared` and `rts-node` already depend on) that both consumers call: `rts-node`'s `node:v8` surface (this module) and, as a follow-up refactor tracked in §5.7, `rts-shared`'s `structuredClone()` .ts — instead of `rts-node` re-deriving its own incompatible traversal logic from scratch. This satisfies rts-node's independence constraint (no dependency on `rts-shared` is needed — only on `rts-engine`, which both already share) while genuinely reusing the structured-clone design rather than reinventing it.
  - `Serializer`/`Deserializer`'s class-level API (`writeHeader`/`writeValue`/`releaseBuffer`/`readHeader`/`readValue`/the `_write*`/`_read*` override points) is a **thin `.ts` wrapper** around that primitive's externs (§5.2): `writeValue`/`readValue` call straight into the generic encode/decode walk; the raw `writeUint32`/`writeUint64`/`writeDouble`/`writeRawBytes`/`readUint32`/`readUint64`/`readDouble`/`readRawBytes` methods are direct cursor operations on the in-progress buffer, needed so a subclass's `_writeHostObject`/`_readHostObject` override can compose its own encoding on top of the same buffer. `v8.serialize(value)`/`v8.deserialize(buffer)` skip the class entirely and call the primitive directly (mirroring how Node's own `serialize`/`deserialize` are documented as thin conveniences over `DefaultSerializer`/`DefaultDeserializer`).
  - Reconstructing a semantically correct `Map`/`Set`/`Date` instance (non-primordial classes whose prototype/method wiring lives in `rts-shared`'s `.ts` stdlib) needs class-identity metadata on the wire; `rts-engine::heap::class_registry` may already partially provide this — needs verification at implementation time (§5.7), not assumed. The primordial subset above (undefined through Error) needs no such metadata and is fully implementable without it.
- **`takeCoverage`/`stopCoverage`.** No RTS analog exists today — real V8 coverage relies on per-function/per-branch bytecode execution counters V8's interpreter/JIT tiers maintain natively; Cranelift has no built-in equivalent. A genuine implementation needs **new codegen-level work** in `rts-codegen-new` (emit a counter-increment IR op at each coverable range, gated behind `NODE_V8_COVERAGE`) — a compiler feature, not something achievable inside `rts-node` alone (§7). Until that lands, both functions are documented no-ops — which is itself spec-compliant, since real Node also no-ops without `NODE_V8_COVERAGE` set (§4).
- **`setFlagsFromString(flags)`.** No general flag interpreter is needed or warranted — RTS has no V8-flag namespace; Cranelift optimization/codegen settings are fixed at RTS's own build time. Implemented as: parse the leading token (`--flag-name` or `--flag-name=value`), match against a small explicit whitelist of RTS-meaningful toggles (candidates: `--trace-gc` → an RTS GC-cycle trace println; `--max-old-space-size=N` → adjusts the `heap_size_limit` soft knob above), and **document-and-no-op** anything not on the whitelist — exactly the documented real-Node behavior for unrecognized/post-startup flags, not a parity shortfall.
- **`getHeapSnapshot`/`writeHeapSnapshot`.** RTS's own JSON schema (per §4, not required to match V8's DevTools format): a small, honestly-labeled document — a metadata block, then one entry per live `HandleTable` slot (id, RTS type/`Entry`-variant tag, best-effort `self_size`, and outgoing references derived from the entry's `Shape`/slot layout where applicable) plus a synthetic root entry. Built by walking `rts-engine`'s `HandleTable` shards + `poly.rs`/`shapes.rs`. Chrome DevTools Memory-tab loadability is an explicit **non-goal** for the initial pass (§7) — revisit only if a concrete workflow needs it, at which point RTS could additionally emit the DevTools-specific schema as an opt-in variant without changing the default RTS-native one.
- **`isStringOneByteRepresentation`.** RTS strings are always UTF-8 (no V8-style two-representation Latin-1/UTF-16 split). Implemented as a documented **approximation**: `true` iff every byte of the UTF-8 encoding is `< 0x80` (pure ASCII, a safe subset of "would fit in Latin-1"); a closer Latin-1-range approximation via a proper decode pass is a possible refinement. Documented in code as an approximation of a V8-internal fact RTS does not track, not a claim of measuring real internal representation.
- **`queryObjects(ctor, options)`.** (1) trigger a real GC cycle first (`rts-engine::collector`'s existing mark+sweep entry point), (2) walk all live `HandleTable` entries representing object instances, (3) for each, resolve its `Shape`'s originating class and walk that class's prototype/`extends` chain to check whether `ctor` appears in it — needs class-identity-on-shape metadata; `rts-engine::heap::class_registry` is the existing home for this and should be extended, not duplicated. `format: 'summary'` additionally needs a generic "stringify one object's own enumerable fields" routine, reusing whatever backs `util.inspect`-style formatting elsewhere rather than writing a new one.
- **`GCProfiler`.** `start()`/`stop()` bracket a series of GC cycles; RTS's collector already has a hook-registration point (`rts_engine::heap::handles::install_gc_hook`) that fires around collection — `GCProfiler` registers into that hook, snapshotting `getHeapStatistics()`/`getHeapSpaceStatistics()` immediately before and after each observed cycle, recording `cost` from an `Instant` pair. The single cleanest mapping in the module — no hoist, no new engine capability, purely a consumer of an existing hook.
- **`startCpuProfile`/`SyncCPUProfileHandle`.** RTS has no sampling CPU profiler yet; a real implementation needs periodic-interrupt sampling (timer-signal or dedicated sampler thread reading the target thread's instruction pointer) plus a symbolication table mapping compiled-code addresses back to RTS function names, producing `.cpuprofile`-format output. Nontrivial new native work, distinct from (and harder than) the existing Bun-style manual push/pop frame-stack tracer in `rts-std`'s `trace/` namespace — flagged as a phased, lower-priority item (§5.8/§7).
- **`cachedDataVersionTag()`.** Maps onto a stable per-build fingerprint RTS derives from its own compiler version + build flags + target features — a real, deterministic value analogous in *purpose* (cache-compatibility checking) to V8's tag, not a copy of V8's algorithm; useful once/if RTS grows its own bytecode/IR cache to validate against.
- **`promiseHooks`/`startupSnapshot`.** See §5.3/§5.7 — `promiseHooks` needs Promise-lifecycle call-sites that today live inside `rts-std`'s promise implementation, unreachable directly from `rts-node`; `startupSnapshot` has **no meaningful RTS analog** given RTS's execution model (RTS never enters a V8-style snapshot-build mode) and is implemented as a source-compatible no-op shim: `isBuildingSnapshot()` always `false`; the three callback-registration functions store-and-never-invoke their callback.

### 5.2 ABI surface

Symbol convention: `__RTS_FN_NODE_V8_<NAME>`. Compound/heterogeneous results (heap-statistics objects, heap-space arrays, GC-profiler results) use the same **JSON-blob-over-`StrPtr`** pattern documented in `docs/node-implementation/os.md` §5.2, decoded by a `.ts` shim.

**Handle model.** `Serializer`/`Deserializer`/`GCProfiler`/`SyncCPUProfileHandle`/`CPUProfileHandle`/`HeapProfileHandle` instances are opaque `u64` handles into `rts-node`'s **own** private sharded handle table (same rationale as `node:crypto`'s `Hash`/`Cipheriv` handles — `rts-node` does not extend `rts-engine`'s shared `Entry` enum with node-specific variants).

**Structured-serialize primitive.** The `SERIALIZE`/`DESERIALIZE` rows and the `Serializer`/`Deserializer` `WRITE_VALUE`/`READ_VALUE` rows below all bottom out in the **same** `rts-engine`-resident encode/decode walk described in §5.1 — they are different `extern "C"` entry points into one shared Rust implementation, not independent per-symbol logic.

### 5.3 Async model

- **Overwhelmingly synchronous.** Every function and class method in this module except `CPUProfileHandle.stop()`/`HeapProfileHandle.stop()` (and their `[Symbol.asyncDispose]`) is synchronous, matching real Node exactly (there is no `node:v8/promises` sibling module).
- **`CPUProfileHandle`/`HeapProfileHandle`'s async `.stop()`** must return a real `Promise`. RTS has no background V8 profiler thread to await, so the honest implementation is: run the equivalent synchronous stop-and-collect work, then wrap the already-available result in a Promise via the engine's Promise-construct-and-settle primitive — which today lives in `rts-std` (§5.7 flags the hoist this needs). **No tokio runtime work is actually required** (there is no real async I/O here), only the ability to *construct and settle a Promise value* from native code, presently a `rts-std`-only capability.
- **`promiseHooks`** needs to intercept the *existing* Promise create/settle/before/after transition points inside RTS's own Promise implementation — a `rts-std` dependency today (§5.7).
- **Everything else** (heap stats, serialize/deserialize, coverage stubs, `queryObjects`, `GCProfiler`, `SyncCPUProfileHandle`, `startupSnapshot`) is a direct, bounded, synchronous native call with zero event-loop or tokio interaction — good candidates to implement first, deferring the two Promise-touching pieces (§5.8).

### 5.4 Multithread / worker interaction

- **Heap statistics reflect the whole process, not a single thread/worker — but RTS should scope them per-region like real Node scopes them per-isolate.** In real Node, each `worker_threads` `Worker` has its own V8 isolate with its own separate heap; a worker's `getHeapStatistics()` reports **that worker's own heap**, not the main thread's. Under `docs/specs/rts-threading-model.md`'s per-thread-region + shared-heap-with-promotion model, this module's stats functions should report figures **scoped to the calling RTS thread/region** when called from a worker, and main-region figures from the main thread — mirroring real Node's per-isolate-heap behavior rather than flattening everything into one process-wide number. This needs the `HandleTable`/collector stats machinery to be queryable per-region, which may require new plumbing if today's shard-scan is process-global only (verify at implementation time).
- **`GCProfiler`/`startCpuProfile` are inherently per-calling-thread/region observations** in real V8 too (each isolate profiles itself) — same per-region scoping applies.
- **`setFlagsFromString`** — real V8 flags are typically process-global (affect every isolate/worker) though many only take effect pre-initialization. RTS's curated-whitelist implementation should treat the handful of supported flags as process-wide mutable state (akin to `os.setPriority`'s process-wide side effect, `docs/node-implementation/os.md` §5.4), not `threadLocal` — a flag set from one worker affects the whole process.
- **`serialize`/`deserialize`/`Serializer`/`Deserializer`** are the mechanism `worker_threads`' `postMessage`/`structuredClone` rely on for cross-thread data transfer. Per the RTS threading model, an `ArrayBuffer` "transferred" via `Serializer.transferArrayBuffer` should map onto an actual **shared-heap promotion** event (the buffer's ownership crosses from one thread's region to the shared heap or directly to the receiving thread's region) rather than a deep copy — the same mechanism `SharedArrayBuffer`/`MessagePort` need generally, not something to reinvent for `node:v8` alone.
- **`promiseHooks`** registered from one thread should (matching real V8, which is per-isolate) only observe Promises created/settled **on that same thread/region** — not a global cross-thread firehose. This needs the hook-registration table (§5.1/§5.7) to be per-thread-scoped, consistent with the `GCELLS`-thread-local discipline already used elsewhere in the codebase.
- **`queryObjects`'s "current execution context" scoping** maps onto "the calling thread/region's shape/handle universe" under the RTS threading model — objects owned by other threads' regions should not be matched.

### 5.5 Buffer / TypedArray interop

- **`serialize()`/`Serializer.releaseBuffer()` return `Buffer`** (which `extends Uint8Array` per the engine's primordial TypedArray model) — the native side allocates raw bytes from the structured-serialize primitive and returns them wrapped as a `Handle` the `.ts` shim exposes as a `Buffer` instance, exactly like every other byte-producing `rts-node` function.
- **`deserialize(buffer)`/`new Deserializer(buffer)` accept `Buffer | TypedArray | DataView`** — the native side reads the underlying `ArrayBuffer` bytes regardless of which view type wraps it (offset+length aware, not assuming a `Buffer`-specific layout), per the engine's primordial TypedArray/`ArrayBuffer`/`DataView` model.
- **`writeRawBytes`/`readRawBytes`** are direct raw-byte-span operations — straightforward `StrPtr`-style (ptr+len) passes across the ABI.
- **`DefaultSerializer`'s typed-array encoding** stores only the *view's* portion of the referenced `ArrayBuffer` (offset + length), not the whole backing buffer if the view doesn't cover it entirely — must be preserved faithfully (a `Uint8Array` view over bytes 10..20 of a 1000-byte `ArrayBuffer` must round-trip to exactly that 10-byte view) to avoid a subtle round-trip-size bug.
- **Heap snapshots/`queryObjects` summaries** may need to render `Buffer`/`TypedArray` contents in truncated/summarized form rather than a full byte dump, for anything beyond a small threshold.

### 5.6 Doctrine placement

`node:v8` is **non-primordial** — the engine (`rts-codegen-new`) must never hardcode `"v8"` or any of its member names. Resolution follows the same `NodespaceSpec` data-table mechanism used by every other `node:*` module in this spec series: `import v8 from 'node:v8'` resolves through `rts_node::ns_prefix_for("node:v8")` → `"node_v8"` (pure data lookup against `NODE_SPECS`, zero hardcoded arm in codegen), and each call such as `node_v8.getHeapStatistics()` resolves via `rts_node::node_lookup("node_v8.getHeapStatistics")` to a `NodespaceMember` (`symbol`, `args`, `returns`) — the generic path every `node:*` module already uses; `node:v8` adds a new `crates/rts-node/src/v8/mod.rs` module (following the existing `crypto/`/`fs/`/`os/`/`path/`/`process/`/`util/` sibling layout) registered in `NODE_SPECS`.

**This is also where the module's central rule lives, restated as a doctrine consequence, not just a framing choice:** per the binding no-V8 rule (`architecture.md` §11, core decision 3), no code path in `rts-node`'s `v8/` module or its `.ts` shim may embed, shell out to, dlopen, or link a real V8 build, and no field returned by this module may be a literal V8 number captured from elsewhere — every value is computed from RTS's own `rts-engine` state as described in §5.1, even where that means reporting an honest, clearly-labeled placeholder rather than a fabricated-but-plausible V8-shaped number.

Native-extern / `.ts`-shim split: every symbol in §5.2 is a raw primitive (scalar getter, JSON-blob getter, or handle-based stateful-object operation). All JS-shape ergonomics — the `HeapStatistics`/`HeapSpaceStatistics[]`/`GCProfilerResult` object construction from decoded JSON, the `Serializer`/`Deserializer`/`DefaultSerializer`/`DefaultDeserializer`/`GCProfiler`/`SyncCPUProfileHandle`/`CPUProfileHandle`/`HeapProfileHandle` class wrappers (including `[Symbol.dispose]`/`[Symbol.asyncDispose]` wiring and the protected override points as real overridable prototype methods), the `promiseHooks`/`startupSnapshot` namespace-object assembly, and `getHeapSnapshot()`'s JSON-string-to-`Readable` wrapping — live in a `.ts` shim shipped by `rts-node` (e.g. `rts-node/src/v8/v8.ts`), matching the project-wide "no high-level API in Rust" design rule.

### 5.7 Shared-infra dependencies (FLAG)

Unlike most other `node:*` modules, `node:v8`'s **bulk** functionality (heap stats, serialize/deserialize of primordial values, coverage stubs, `GCProfiler`, `SyncCPUProfileHandle`, `queryObjects`) needs **no hoist at all** — it is backed by `rts-engine` internals `rts-node` already depends on directly. The exceptions, which do need infra that currently lives in `rts-std` (or doesn't exist anywhere yet):

- **Promise construction/settlement for async `.stop()`.** `CPUProfileHandle.stop()`/`HeapProfileHandle.stop()` must return a real, resolvable `Promise`. The primitive that constructs-and-settles a Promise from native code (`promise.create(fn, args)`, `rt.spawn_blocking` + settle) lives in `rts-std` per the crate partition; `rts-node` cannot depend on `rts-std`. **Needs:** either (a) a minimal Promise-construct-and-settle primitive hoisted into `rts-engine` itself, reachable by any crate depending on `rts-engine` (including `rts-node`) without pulling in the full tokio machinery `rts-std`'s version needs for genuinely async work, or (b) a `rts-node`-local "already-settled Promise" construction path if the engine's Promise ABI allows building an already-resolved Promise without touching tokio at all. Owner decision needed.
- **Promise-lifecycle hook call-sites for `v8.promiseHooks`.** The actual create/before/after/settled transition points execute inside `rts-std`'s promise implementation — unreachable from `rts-node` directly. **Needs:** a hook-registration table hoisted into `rts-engine`, analogous to the **already-existing** `rts_engine::heap::handles::install_gc_hook` pattern used for GC-cycle hooks — `rts-std`'s promise code calls into this table at each lifecycle transition; `rts-node`'s `v8.promiseHooks` registers/unregisters callbacks into the same table. A clean, precedented shape for the hoist, not a novel design.
- **Shared tokio runtime (`rts-std::runtime::async_rt`)** is needed only **transitively**, via the Promise-construction primitive above — `node:v8` itself performs no I/O, no timers, no genuinely concurrent work. If the "already-settled Promise" minimal path (option (b) above) is chosen, no tokio dependency is needed for this module at all.
- **One shared structured-serialize primitive, and unifying it with `structuredClone()` (§5.1).** The primordial-value encode/decode walk needed for `serialize`/`deserialize`/`Serializer`/`Deserializer` is fully reachable today from `rts-engine` alone — **no hoist blocks the primordial subset**. What does need a decision: whether to actually **refactor** `rts-shared`'s existing `structuredClone()` `.ts` walk to call this new native primitive too (recommended, for one source of truth on value-traversal semantics — e.g. exactly how a `Date`/cyclic reference/`TypedArray` view is handled should not silently diverge between the two entry points), or accept the two implementations coexisting with separately-maintained semantics. This spec recommends the former as the correct target architecture but does not execute the `structuredClone()` refactor itself (out of scope for `node:v8`'s own implementation pass) — flagged for coordination with whoever owns `rts-shared/src/stdlib/structured_clone.ts`.
- **Non-primordial container class-identity for faithful `Map`/`Set`/`Date` serialization and for `queryObjects` matching against user-defined classes extending them.** The `.ts`-level prototype/method wiring for `Map`/`Set` lives in `rts-shared`'s `.ts` stdlib — `rts-node` cannot depend on `rts-shared`. **Needs:** verification of how much class-identity metadata `rts-engine::heap::class_registry` (already reachable) can supply on its own; if insufficient to distinguish "this shape is specifically a `Map` instance" from a similarly-shaped plain object, a small amount of class-tag metadata needs to be surfaced at the `rts-engine` level (not the full `rts-shared` `.ts` implementation) for `rts-node` to consume. Flagged as **needs verification at implementation time**, not a fully specified hoist yet.
- **Real per-function/branch coverage counters for `takeCoverage`/`stopCoverage`.** Not infrastructure living in `rts-std` today — it doesn't exist anywhere yet. Needs new instrumentation support in `rts-codegen-new` itself (emit counter-increment IR at coverable ranges). A **compiler feature gap**, not a `rts-std`-hoist item; see §7.
- **Sampling CPU/heap profiler infrastructure for a *real* `startCpuProfile`/(future) `startHeapProfile`.** Also does not exist anywhere in the codebase today (the existing `trace/` namespace is a manual push/pop frame stack, not a statistical sampler) — new native work (signal/timer-based sampling + symbolication), not a hoist. See §7.

### 5.8 Implementation phases

1. **(a)** Stand up `crates/rts-node/src/v8/mod.rs` with the `NodespaceSpec` skeleton (`node_module: "v8"`, `ns_prefix: "node_v8"`) and register it in `NODE_SPECS`, following the `crypto/`/`os/` sibling pattern.
2. **(b)** Implement the heap-statistics group (`getHeapStatistics`/`getHeapSpaceStatistics`/`getHeapCodeStatistics`/`getCppHeapStatistics`) reading real figures from `rts-engine`'s `HandleTable`/collector where available, with the documented placeholder fields (`does_zap_garbage`, `number_of_native_contexts`, etc.) clearly marked in code comments. Add the tracking-allocator/heap-limit knobs this needs if they don't already exist.
3. **(c)** Implement `cachedDataVersionTag`, `setFlagsFromString` (curated whitelist), `isStringOneByteRepresentation` (ASCII/Latin-1-range approximation), `takeCoverage`/`stopCoverage` (as documented no-ops absent real instrumentation — see §7) — the small, self-contained items with no cross-module dependency.
4. **(d)** Implement the **shared structured-serialize primitive** in `rts-engine` for **primordial** value types first (undefined/null/bool/number/bigint/string/Array/plain Object/ArrayBuffer/TypedArray/DataView/Date/RegExp/Error), then `serialize`/`deserialize`/`Serializer`/`Deserializer`/`DefaultSerializer`/`DefaultDeserializer` as thin consumers of it — the highest-value, most-reused piece of this module (also what `worker_threads` `postMessage` will eventually want, and the piece §5.7 recommends `structuredClone()` migrate onto). Defer `Map`/`Set`/host-object (`_writeHostObject`/`_readHostObject`) support to a follow-up once the §5.7 class-identity question is resolved.
5. **(e)** Implement `GCProfiler` via the existing `install_gc_hook` mechanism — low native-work item given the existing hook, high diagnostic value.
6. **(f)** Implement `queryObjects` (count + summary formats) once `class_registry` coverage is confirmed sufficient (§5.7); implement `SyncCPUProfileHandle`/`startCpuProfile` only after evaluating the sampling-profiler design question in §7 (may land later than (a)-(e) given its size).
7. **(g)** Implement `getHeapSnapshot`/`writeHeapSnapshot`/`setHeapSnapshotNearHeapLimit` against RTS's own minimal JSON schema (§5.1) — no DevTools-schema work in this pass; wire `setHeapSnapshotNearHeapLimit` to the `heap_size_limit` knob from (b).
8. **(h)** Resolve the §5.7 Promise-construction/hoist question with an owner decision, then implement `v8.promiseHooks` and the async `CPUProfileHandle`/`HeapProfileHandle` classes (deferred until (h) regardless of whether their public starter functions ship in this Node-25-targeted pass, given the §7 verify-flag on whether they're even reachable via a public function in Node 25 itself).
9. **(i)** Implement `v8.startupSnapshot` as the documented no-op shim (§5.1) — trivial, no dependencies, can land any time after (a).
10. **(j)** Cross-cutting: confirm `using`/`await using` language support exists (or lands) before shipping `GCProfiler`/`SyncCPUProfileHandle`'s `[Symbol.dispose]` wiring as anything beyond a plain callable `.discard()`-style method; retrofit the `using` sugar once the language feature lands if it's not ready first.

## 7. Open questions / deferrals

Governed throughout by the binding no-V8 rule (`docs/node-implementation/architecture.md` §11, restated in §5.6): none of the items below are resolved by "link/shell out to V8" — every open question is about which RTS-native mechanism to build or extend.

- **`CPUProfileHandle`/`HeapProfileHandle` reachability in Node 25 itself is unclear and needs re-verification against the released v25.x docs at implementation time.** Both classes are documented on the current `nodejs.org/docs/latest-v25.x/api/v8.html` page (`CPUProfileHandle` added v24.8.0, `HeapProfileHandle` added v24.9.0), but no public function on that page is documented as *returning* either of them — the one starter function that does exist for the async heap-profile case, `v8.startHeapProfile([options])`, is tagged "Added in: v26.1.0" and "Stability: 1 - Experimental" on Node's **main-branch** (post-25) docs, i.e. it postdates the Node 25 line. It is possible these two classes are present in the v25 docs purely as forward-looking/prepared surface, or that a starter function exists under a name not surfaced by the fetches performed for this spec. **Action for implementer:** re-check the exact installed Node 25.x minor/patch version's docs (or its TypeScript `@types/node` definitions) before building these two classes; if no reachable public constructor exists in the target Node 25.x version, these two classes may be legitimately out of scope for this pass and `SyncCPUProfileHandle`/`startCpuProfile` alone cover the "supported" CPU-profile surface.
- **Byte-level V8 wire-format compatibility for `serialize`/`deserialize`.** Explicitly deferred (§4) — RTS's wire format is internally self-consistent but not required to match real V8's tag bytes, since Node itself does not guarantee this across its own versions. Revisit only if a concrete use case needs to read/write files produced by real Node's `v8.serialize()` (e.g. a shared on-disk cache format with a real Node process) — not needed for RTS-to-RTS `postMessage`/`structuredClone`.
- **Heap-snapshot Chrome DevTools fidelity.** Out of scope by default (§4/§5.1) — RTS ships its own minimal JSON schema. Whether to additionally emit a DevTools-loadable variant (so the Memory tab can load it, even with approximate/best-effort retainer-edge data) is an open scope question for a future pass, not required for `node:v8` parity as documented by Node itself.
- **Real bytecode/branch coverage (`takeCoverage`/`stopCoverage` producing genuine per-file coverage JSON).** Requires new `rts-codegen-new` instrumentation (counter-increment IR at coverable ranges gated by `NODE_V8_COVERAGE`) — a compiler feature, not a `rts-node`-local task. Needs an owner decision on priority relative to other codegen work; until it lands, `takeCoverage`/`stopCoverage` are documented no-ops (itself spec-compliant per §4's note that coverage is opt-in via an env var Node itself may not have set).
- **Real sampling CPU/heap profilers.** `startCpuProfile`'s honest implementation needs a genuine sampling mechanism (signal/timer-based instruction-pointer capture + symbolication against Cranelift-compiled-code address ranges) — meaningfully new native work, likely its own multi-step epic rather than a one-off inside this module's implementation pass. A first-cut alternative (flagged for owner sign-off, not decided here) could report an honestly-labeled degraded profile (e.g. wall-clock total + call-count-based approximation from existing `trace/`-namespace frame data) rather than blocking the whole module on a full sampling profiler — but this must be clearly distinguishable from a real sample-based `.cpuprofile` and never presented as equivalent fidelity.
- **`node:v8`'s "current execution context" / realm scoping for `queryObjects` and heap stats**, mapped onto RTS's per-thread-region threading model (§5.4), needs the threading-model spec (`docs/specs/rts-threading-model.md`) and this module's implementation to agree on exactly what "region-scoped" means operationally (e.g. does a shared-heap-promoted object get miscounted/double-counted across regions?) — flagged for cross-checking against that spec once T-phase work is further along.
- **Promise-construction hoist decision (§5.7)** — whether to hoist a minimal Promise-construct-and-settle primitive into `rts-engine`, or accept a `rts-node`-local "already-resolved Promise" shortcut for this module's synchronous-under-the-hood needs, is an explicit owner decision this spec does not resolve.
- **Unifying `structuredClone()` onto the new structured-serialize primitive (§5.1/§5.7).** This spec recommends refactoring `rts-shared`'s `.ts` deep-clone walk to call the same native primitive `node:v8` introduces, for one source of truth on value-traversal semantics, but does not execute that refactor — needs coordination with whoever owns `structured_clone.ts`, and sign-off that the primordial-subset primitive is a strict superset of what `structuredClone()` needs today.
- **`using`/`await using` language-feature timing.** If TC39 Explicit Resource Management support in RTS's parser/HIR is not ready when this module is implemented, ship `GCProfiler`/`SyncCPUProfileHandle`/(future async handles) with their `stop()`/discard methods fully functional as plain method calls first, and retrofit `[Symbol.dispose]`/`[Symbol.asyncDispose]` + `using` sugar once the language feature lands — do not block this module's core value (heap stats, serialize/deserialize, GC profiling) on an unrelated language-feature dependency.

# The performance work list, 2026-09-27

**What produced this.** Six stages of measured optimisation landed on `main`
between 2026-09-26 and 2026-09-27 (commits `530101cda`, `090cda78b`,
`40c92c718`, `71d90c95e`, `c9384593a`, `d718a12d4`), each ranked from the same
instrument: `bench/analytic.ts` sorted by the engine's ABSOLUTE nanoseconds per
row — never by the ratio to Node, whose rows under a nanosecond are dead-code
elimination and rank nothing. What follows is what is still on that list, in the
order it would be attacked, with the number each row costs today, the cause
where it was verified at a `file:line`, and the experiment that would settle it.

**How the numbers were taken.** Release binary of `d718a12d4`
(`target/release/rts.exe`, `cargo build --release`), this machine, 2026-09-27,
one process per row where a row allocates (`docs/codegen/README.md` rule 4a).
The `iso_*.ts` files named below are the per-row harnesses used for the six
stages; they follow `bench/analytic.ts`'s own rules (warm-up call, `KEEP` escape,
checksum printed). A row from `bench/analytic.ts` itself says so.

**It is a plan, and plans go stale.** `docs/README.md` rule 1: when an item here
lands or is refuted, edit it here in the same change. [`plan.md`](plan.md) is the
list of 2026-08-21; its ranking is superseded by this one, and its refutations
("what I am NOT proposing") still stand and are not repeated here.

## Compile latency, measured 2026-09-27 — and why copy-and-patch is not a candidate yet

Asked because a tier-0 backend (copy-and-patch, as CPython 3.13 and LuaJIT-Remake
use) was proposed for the time a large file takes to start. Measured first, on
`bench/analytic.ts` with its runner removed so that nothing executes (release
`d718a12d4`, 16 cores, `RTS_TIMING=1`, three runs each):

| stage | wall |
|---|---:|
| an empty program (`console.log(1)`), the process floor | 55 ms |
| front-end (parse, check) | 41 ms |
| emit (both emitters, the MIR passes) | 35 ms |
| `place` (Cranelift lowering + machine compile + JIT) | 183 ms |
| total | 295 ms |

Inside `place`: 293 ms of CPU serially over 396 functions, and **183 ms of wall
with sixteen threads** (`RTS_CRANELIFT_JOBS=1` 320, `=2` 256, `=4` 214, `=8`
196, `=16` 183). The pool is not the limit; ONE function is. `rts prove` puts
the program's entry — the module body, 277 `bench(…)` calls and their closures
— at **6 731 instructions against 218** for the next largest, and that function
alone takes about 175 ms. With `RTS_CL_REGALLOC=single_pass` (measured only:
`target/mod.rs` records that it generated wrong machine code for the largest
program here, which is why it is not the default) `place` drops from 183 to 83
ms — so about 100 ms of the 175 is the backtracking register allocator being
superlinear on one giant function, not Cranelift's cost per instruction.

**LANDED 2026-09-29** as `emit/chunk.rs`: runs of top-level statements that
declare nothing become `function <module N>() { … }` and a call, sixteen
statements a piece, where a body has at least forty-eight of them. Same file,
same machine, release, three runs each, `RTS_CHUNK=0` against the default:

| | whole body | split |
|---|---:|---:|
| `lower+compile` | 204 / 221 / 224 ms | 40 / 42 / 41 ms |
| total wall of the file | 354 / 329 / 329 ms | 168 / 185 / 168 ms |

The first version existed and never ran: its probe read a `return` inside an
ARROW as the module's own and admitted 3 statements of 315. Every correctness
gate was green; the function count in `RTS_TIMING` (396 both ways) is what said
so. Run rows are unchanged with the split on or off when measured on an idle
machine; a first comparison taken while the suite was starting showed three
`Map.get` rows 40–90% slower, which was the machine and not the change.

What the paragraph below proposed, kept for the reasoning:

**What follows.** A tier-0 backend attacks the per-instruction cost, which is
not what dominates. The candidate is the SHAPE of the entry function:

- **Split the module body into chunks** — sequential functions of a bounded
  instruction count, called in order by the entry, with the module's
  bindings already living in an environment object rather than in registers,
  which is what makes the split a lowering change and not a semantic one. It
  turns a superlinear cost into a linear one on the run-once code every large
  file has; the expected order is 175 → 30 ms, to be measured, not assumed.
  Experiment: the same file with the body split by hand into functions of
  ~500 instructions, before touching the emitter.
- Only after that, if the per-instruction cost is what remains: Cranelift is
  already at `opt_level = none`, so the remaining lever would be a cheaper
  register allocator for run-once code — and `single_pass` is the one that
  was measured to miscompile, so that door needs the miscompile found first.

Copy-and-patch stays what `docs/README.md` calls an idea: no experiment says
the per-instruction cost is the problem, it needs a C toolchain in the engine's
build (the availability rule `text/narrow.rs` already applied against mimalloc),
a stencil per instruction per target, and a second statement of the frame and
collector contracts `lower/` states once. Re-open it the day the chunked body
still costs what the file cannot afford.

## The list

### 1. `f(...xs)` and `f.apply(o, [a])` — the array is the cost

| row | now | ruler |
|---|---:|---|
| `f(...xs)`, three elements | 536 ns | `iso_calls.ts`, 5M |
| `f.apply(null, [a])` | 248 ns | `iso_calls.ts`, 5M |
| `f.apply(null, xs)` with `xs` hoisted | not measured — measure first |

**Verified cause.** For `.apply` the door is already direct
(`function_direct.rs::function_apply_direct`) and reads the elements straight
from the store; `f.call(null, a)` through the same protocol costs 88 ns, so the
160 ns difference is the `[a]` literal: a cell, an element store and a collection
brought closer, on every iteration. For `f(...xs)` the spread builds an argument
vector (`ArrayOf`, `runtime/mod.rs`, eight slots) and the callee reads it back
through `pending_arguments` (`functions.rs::collected`).

**Approach.** A spread whose operand is a real array with at most
`ARGUMENT_SLOTS` elements can be passed in the slots, with the count, exactly as
`function_apply_direct` already does — the door exists, what is missing is the
emitter recognising `f(...xs)` as its caller. The literal in `.apply(o, [a, b])`
is the emitter's to see too: the elements are written at the site, so they can
go in the slots without the array ever existing, under the same `Function`
proof.

**Experiment.** `bench/isolated`: one row that builds a three-element array and
reads it back against one that passes three values; the engine's shape first.

**Cost.** One more shape in `emit/methods` and `lower/intrinsic.rs`, and the
array-like semantics stay behind the fallback (`apply_to`), which is where a
length getter or a hole must still be observed.

### 2. A bound function called — 360 ns

| row | now | ruler |
|---|---:|---|
| `b(a)` where `b = f.bind(null)` | 360 ns | `iso_calls.ts`, 5M |

**Cause, partly verified.** `function_proto.rs::bound` makes a native whose
call rebuilds the partial arguments and the receiver and then calls through
`call_with_args` — the vector path, the one `f(...xs)` also pays — even when the
partials are none and the arguments fit the slots. The exact split between the
native dispatch and the vector was NOT measured; measure before acting.

**Approach.** A bound function with no partials and a call that fits the slots
is `call_counted(target, bound_this, …)` with the slots as they arrived. The
partials case can prepend into the slots while they fit.

**Experiment.** `rts ir` of the bound call shows only the ordinary call door;
the cost is inside the runtime, so a `rts-core` harness row
(`examples/entry_cost.rs`) with a bound native called a hundred thousand times,
split with and without partials.

### 3. `toPrecision` — 1 250 ns, still the sixty-digit expansion

| row | now | ruler |
|---|---:|---|
| `(i + 0.5).toPrecision(4)` | 1 250 ns | `iso_fmt.ts`, 2M |

**Verified cause.** `number/format.rs::carried` (line 208) asks
`format!("{:.*}", expansion_places(...))` — the same big-integer expansion
`toFixed` used before `number/fixed.rs`, and for the same reason: the tie rule
is the specification's, not Rust's.

**Approach.** The integer form `fixed.rs` uses, with one more step: the scale is
`10^(p - 1 - e)` where `e` is the decimal exponent of `x`, so the digit count has
to be found first — from `e = floor(log10 x)` corrected by one comparison
against `10^e`, since `log10` can be off by one at a boundary. Negative exponents
multiply by `10^k` with `k` up to `p - 1 - e`, which overflows `u128` for tiny
values; those keep the expansion. `toExponential` shares `carried` and would
move with it.

**Experiment.** The same unit test shape as `fixed.rs`: forty thousand bit
patterns against `carried`, every precision from 1 to 21.

**Cost.** A second exact formatter beside `fixed.rs`; the module header must say
which cases fall back and why, or the fallback becomes a silent second path.

### 4. The dispatch on a primitive receiver — the 88 ns of `f.call`, and the other string members

*`s.charCodeAt(i)` left this item on 2026-09-29 (70 → 13 ns). `s[i]`, `at`,
`codePointAt` and the rest of `String.prototype` still pay the dispatch.*

| row | now | ruler |
|---|---:|---|
| `s.charCodeAt(1)` | 64 ns | `iso_fmt.ts`, 2M |
| `f.call(null, a)` | 88 ns | `iso_calls.ts`, 5M |
| `f(a)` direct, for scale | 4 ns | same |

**Verified cause, two halves.** A method on a string goes through
`objects.rs::get_property` → `computed::primitive_found` (`objects.rs:148`),
which walks to `String.prototype` on every call and then dispatches the native
through `functions::called` — which pushes and pops `pending_arguments` and
`pending_counts` inside two `with_current` borrows (`functions.rs:741-760`) on
EVERY call, direct or not. `f.call`'s remaining 88 ns is that protocol plus
`function_direct.rs::plain_function`: three lookups, one of which interns the
key `call` through `well_known` — not one of the cached spellings, so it hashes
the text each call.

**Approach.** Two independent pieces. (a) `call` and `apply` join `CACHED_KEYS`,
which is one line each and removes a hash per call. (b) The protocol: the two
pushes exist so that `arguments`, `argument_at` and the variadic natives can
find the running call's vector and count. A call whose callee is a native the
runtime knows takes no `arguments` object — so the pushes could be skipped for
natives, if every reader of `pending_*` is audited for the native case. That
audit is the work; `native-call-floor.md` measured the same 35 ns floor from the
other side and is the document to extend rather than duplicate.

**Experiment.** `examples/entry_cost.rs` already exists for exactly this; add a
row that calls a native through `called` with and without the two pushes.

**Cost.** (b) touches the one place every call passes through; a reader of
`pending_counts` that is missed answers a wrong `arguments.length` silently.
`tests/arguments_light.test.ts` and `tests/arguments_object.test.ts` are the
rulers for that.

### 5. `toString(16)` — 175 ns after the direct entry

| row | now | ruler |
|---|---:|---|
| `i.toString(16)` | 175 ns | `iso_fmt.ts`, 2M |
| `i.toString()` for scale | 79 ns | same |

**Verified cause.** `format::in_radix` (`format.rs:78`) builds a `String` by
repeated division and pushes, then `Str::from_str` copies it: two buffers for
a text that is inline in the `Str` anyway. For an integer below `2^53` the digits
fit a stack buffer of 64 bytes.

**Approach.** Write the digits into a `[u8; 64]` from the end and build the
`Str` from the slice, as `arguments.rs::spell` does for a decimal index.
The fractional path (twenty places) can keep the `String`.

**Experiment.** `examples/string_cost.rs` row: `in_radix(255, 16)` today
against the stack form.

### 6. Regular expressions — the largest absolute rows, causes NOT verified

| row (`bench/analytic.ts`) | now |
|---|---:|
| `new RegExp` per call | 2 156 ns |
| `replace` with a function | 1 636 ns |
| `exec` with a named group | 1 535 ns |
| `split` by regex, 8 pieces | 685 ns |
| `test`, long subject | 486 ns |

**What is known.** `crates/rts-core/README.md` rule 5 names `regex` and
`fancy-regex` as the matchers; `new RegExp(source)` per call compiles a pattern
per call, which is the row's whole meaning, and a cache keyed by source and flags
is the obvious first experiment. The other four are matches on a compiled
pattern and their cost is unattributed — the match itself, the result object,
the captures materialised as strings, or the callback protocol for `replace`.

**First step, before any change.** `rts ir` on one program per row to see which
entry is called, then `examples/entry_cost.rs`-style rows that time the matcher
alone against the entry. Nothing here is a candidate until that split exists;
`docs/codegen/README.md` rule 1 is what says so.

### 7. `JSON.parse` / `JSON.stringify`, nested — 1 194 / 790 ns

**What is known.** Both are one entry each and allocate per node; `parse` builds
objects through `put` with shape transitions per key. The `lost-roots.md`
history says the parser's rooting was already reworked once, which is a reason
to measure before touching it. Unattributed beyond that; the same first step as
item 6.

### 8. `String(obj)` — 1 047 ns, and `date.toISOString` 640

Both allocate several intermediate strings for one answer. `String(obj)` runs
`ToPrimitive` (a user `toString` where there is one, else the tag form
`[object Object]` built from parts) and then interns; the tag form is a fixed set
of texts that could be cached values like `CACHED_TEXTS`. `toISOString` formats
through `format!` piecewise. Unverified split; measure first.

## A regression the direct doors introduced, found 2026-09-29

The collection doors of `530101cda` were chosen by the MEMBER'S NAME, so every
receiver that was not a collection paid the entry's fallback, which reads the
method with no inline cache. Answers were right; the cost was not. A user class,
release, 10M iterations, the binary before the doors against the one after:

| member of a user class | before the doors | with them |
|---|---:|---:|
| `.get(k)` | 25.3 ns | 108.2 |
| `.has(k)` | 23.7 | 109.1 |
| `.add(k)` | 27.7 | 117.2 |
| `.push(k)` | 24.0 | 116.1 |
| `.fetch(k)`, `.check(k)` — other names | 25.0 | 25.4 |

Nothing caught it: the fixtures pin answers, and the isolated rows and
`bench/analytic.ts` measure the door on REAL collections only. It was found by
measuring an ordinary method call for another reason and seeing one name cost
four times its neighbour. **The lesson for every door: measure the receiver it
is NOT for.** `emit/evidence.rs` is the fix — a door is emitted only where the
program's text expects a collection — and its header has what counts.

## Indexed reads — what the door bought and what it cannot

`a[i]` went from 14.6 to 9.6 ns and no further, and the remainder is the floor
of a call into the runtime, not work: the read itself is one load. The form a
C++ compiler emits — a bound check and a load from a base address — is the
`Inst::ElementLoad` that `element-load.md` records as written, measured at
−15 %, and REFUSED because a base address derived from the array stops being a
root the conservative scan can see. That is unchanged. Node reads the same
element in 0.7 ns, so the gap that is left is the keystone
(`docs/engine/the-unwired-keystone.md`), not another door.

Two things the fixture for this stage found that are NOT fixed here, because
the binary before the change answers the same: `null[n]` with a numeric `n`
answers `undefined` where the language raises a `TypeError`, and a getter
defined on an array INDEX with `Object.defineProperty` is not read. Both are in
the generic indexed read and were left out of `tests/index_direct.test.ts`
rather than pinned wrong.

`rts-host --test suite` (the in-process fixtures of `crates/rts-host/tests/suite/`)
fails with `TypeError: the value is not iterable` on a clean tree at `90c16e617`,
before any change of 2026-09-29. It is one process for every fixture, so the
first uncaught exception ends the run and hides the rest — seven of its
fixtures raise one when run alone. It needs its own look.

## Method, so the next stage is measured the same way

1. `cargo build --release && cp target/release/rts.exe target/baseline.exe`
   before the first edit (`CLAUDE.md`, the kept binary).
2. One `iso_*.ts` per row, alternated baseline/now three times; a row that moves
   in one binary only is noise until it moves in both directions of the
   alternation.
3. `RTS_BIN=… bash scripts/suite_per_file.sh` for both binaries and `join` for
   LOST/GAINED; the net number is never the claim.
4. `cargo test --profile fast --no-fail-fast -p rts-mir -p rts-cranelift
   -p rts-codegen -p rts-core -p rts-host`, with `cargo build --profile fast
   -p rts-runtime -p rts-runtime-jit` first so the AOT test sees a fresh archive.
5. The commit carries the before/after table and what was rejected; this file
   loses the row in the same commit.

Two things the six stages taught that are not written anywhere else. Under the
MIR door a loop counter has no type until the inference has run, so a rewrite
that depends on the receiver being a number belongs in a post-inference pass
(`optimize/number_methods.rs`, `optimize/template.rs`) and not in the lowering.
And every TypeScript body spells a read of something typed `any` through an
assertion (`(arguments as any)[i]`), which is erased and names the same value:
a classifier that does not look through `ExprKind::Asserted` exists without
ever firing, and nothing but the clock says so.

## Done 2026-09-29 — the light call

A function that reads none of its activation's argument record (`arguments`, a
rest parameter, a fifth parameter, `new.target`, `eval`; not `async`, not a
generator, strict) is called by the door without the two argument stacks.
`emit/light_call.rs` is the rule, `rts-core`'s `entry/light_call.rs` the
measurement and the two designs that lost: the compiled site making the jump
itself (light callee faster, every other callee 5 to 6 ns slower), and the
answer carried as a bit of the arity.

Release, `bench/analytic.ts`, against the tree before it: `ic call mono` 37.5 →
23.8 ns, `call recursion depth 8` 26.6 → 16.8, `call closure capture depth 3`
21.6 → 14.8, `coll Map.has` 37.3 → 26.7; a callee that is NOT light is
unchanged (`call arguments object` 23.8 → 24.1, `call through a variable` 20.8
→ 20.2). Geomean over 232 rows 0.983. Rows that read 10 to 16% slower in that
run and touch no call (`prop instanceof`, `binary Float64Array rw`) were not
isolated; they are recorded here rather than explained.

## Measured 2026-09-29 — where an allocation's time goes, and what did not help

Release. `examples/alloc_cost.rs` and `iso_class.ts` (an escaping object per
iteration, 3 000 000 of them).

| | ns per object |
|---|---:|
| a cell taken from the free list, no collector (`pre-freed`) | 14.4 |
| the collector's bookkeeping for it (`sweeping` − `pre-freed`) | 13.3 |
| an object literal `{a}` that escapes, whole | 49–50 |
| `new E()`, after `construct_plain` | 72–75 |

So a literal is 28 ns of cell and 22 of making an object out of it, and `new`
is 22 to 25 on top of the literal. The fields are 3 ns each.

**Refuted: a smaller heap, so that the young space fits the cache.** The
region is 65 536 cells of 128 bytes — 8 MB, walked once per cycle. Built with
16 384 and 8 192 cells instead:

| cells | literal `{a}` | `new E()` | freed per cycle |
|---:|---:|---:|---:|
| 65 536 | 49.4 | 72 | 62 900 |
| 16 384 | 59.5 | 80 | 13 750 |
| 8 192 | 81.5 | 102 | 5 560 |

A cycle has a cost that does not shrink with the heap — marking the 2 571
cells of the built-in world and scanning the stack, 0.15 to 0.25 ms — and a
smaller heap pays it more often. The cache it was meant to win is worth less
than that.

What this says about the order of work: the 27 ns of cell is structural for a
collector that cannot move an object, and it cannot move one while the roots
are conservative (`docs/engine/the-unwired-keystone.md`). What can be removed
without the keystone is the work AROUND the cell — the crossing `new` makes,
the object never allocated because it does not escape — and that is the
compiler's.

## Done 2026-09-29 — a class as a layout, first step

`const o = new C(…)` into a local nothing else sees is compiled as the
fields themselves (`emit/class_layout.rs`): 80.4 → 4.5 ns, beside 3.8 for the
literal written by hand. An instance that escapes is untouched (78 → 77).

Left, in the order it pays:

1. a METHOD called on the instance still makes it exist (`o.norm()`: 92 ns).
   Substituting the method's body with `this` as the fields is what frees it;
2. `extends` of a class with a layout: the parent's fields first, `super(a)`
   as the parent's writes;
3. a class declared in another module of the same program — the proof is per
   file today, as `inline`'s is;
4. the instance that ESCAPES: allocated in its final shape by the compiled
   code instead of through `construct` (77 against 48 for the literal).

## Done 2026-09-29 — a method on a layout

A method that is one expression over its fields and parameters is that
expression at the call: `const o = new F1(i); s += o.get2()` 93.9 → 4.3 ns,
`v.dot()` over two fields 103.6 → 4.6. Item 1 of the list above.

A class now has a layout only where it is NEVER READ AS A VALUE
(`receiver::handed_over`). The step before this one did not ask, and a setter
installed through `C.prototype` from outside would have been skipped by it.

A reading of `bench/analytic.ts` worth keeping: six of its rows are BIMODAL on
one binary — `binary typed for-of 16` reads 151 or 266, `json stringify string
256` 323 or 500 — so one run against one run reported a geomean of 1.044 for
a change that touches none of them, and the minimum of two runs of each
binary reported 1.004. Compare minima, or isolate the row.

## Done 2026-09-29 — `extends` and `super()` on a layout

Item 2 of the list. `new D(i, 2)` into a local 164 → 4.7 ns, three levels
272 → 4.4, a parent's method read through the child 180 → 4.3.

What is left of that list, and one thing found on the way:

- a class declared in ANOTHER MODULE of the program — the proof is per file;
- the instance that ESCAPES: 75 ns for a base class and 157 for a derived

  is used as an object, and the derived figure is twice the base one for a
  reason the layout already knows the answer to;
- `bench/analytic.ts` has no row for an instance that does not escape, so
  none of the last three steps moves it. A ruler that cannot see a 40-fold
  change needs the rows.

## Done 2026-09-29 — the instance that escapes

Item 4 of the list: `new F1(i)` kept 78.8 → 52.6 ns, a derived one 169 → 56,
`{ __proto__: p, a }` 573 → 55. A class with a layout now costs what a
literal costs, seen or not.

What is left for classes:

- a class declared in ANOTHER MODULE — the proof is per file;
- a class that is READ AS A VALUE (`instanceof C`, `export`, passed to a
  call) has no layout at all. `receiver::resolve` already tells a class that
  defines no `Symbol.hasInstance` from one that does; `handed_over` does not
  use it, so `x instanceof C` alone costs a class its layout;
- a method that is more than one expression, or writes a field, is a call
  and makes the instance exist;
- `new E()` on a class with NO fields is still constructed when it is kept
  (74 ns): the rewrite asks for a field to hang the literal on, and an empty
  literal under a prototype would do.

And the collector is now the whole cost of an object that exists: 48 of the
53. `docs/engine/the-unwired-keystone.md` is what moves it.
